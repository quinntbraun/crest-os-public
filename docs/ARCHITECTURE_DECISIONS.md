## Owner decisions recorded 2026-10-20

- Cost target approximately $10/month; use free services where they preserve required behavior. The budget pilot and its capacity/availability tradeoffs are specified in ARCHITECTURE section 9. Cost does not authorize permanent data loss, accounting shortcuts or weaker access controls.
- Recovery, security and backup alerts go to the privately configured owner alert mailbox. Verify ownership and actual delivery; do not send secrets/backups as email attachments. Independent monitor/provider notices must also target this mailbox. No messages or account changes were made by documenting this decision.
- Password plus authenticator TOTP; remember trusted phone/desktop sessions for up to 30 days, expiring after seven days without foreground use. Opening the app does not require a new login. Sensitive export/security/period-unlock actions can require recent authentication. Device loss, recovery or revocation can end a session earlier. Require a unique Crest password; strongly recommend a different unique mailbox password and mailbox MFA. No paid password manager required. An offline sealed recovery kit must include provider recovery material and backup decryption keys, held separately from the phone/email/app; test recovery without the phone. Mailbox-only reset must not bypass TOTP.
- Backups every six hours; 30 daily and 12 month-end points plus referenced originals. Continue financial writes after a 24-hour backup failure with persistent in-app and external email alerts; record the RPO breach. Do not destroy records to meet a storage cap. Retention is provisional preservation, not a legal retention opinion.
- Real duplicate prevention uses stable command identity and verified provider transaction IDs. Same customer/vehicle/service, even on the same day, is not unique payment identity. Flag same-customer/same-amount/same-method/same-business-date receipts for review; display candidate details and allow an explicit reason to confirm a distinct receipt. Flagging never automatically refunds, merges, deletes or rejects a legitimate transaction. Repeated service on a new job is valid; invoice entitlement controls prevent billing the same fulfilled scope twice. Deterministic rules suffice; no AI model required.
- Fresh prospective accounting start; no historical ledger import. Technical cutover/opening controls are adopted; actual local date/time and evidenced amounts remain activation inputs. Fresh start is not permission to assert zero cash, unpaid invoices, deposits, debts or assets. Import reviewed legacy customers and their vehicles/contact details through preview/mapping/reconciliation, with no financial posting. Preserve source batch and identifiers; no guessed field mapping or automatic merges.
- Mobile and Customer Drop-Off enabled at launch. Pickup + Return remains separately gated. Existing condition/custody/acknowledgement requirements still apply; enabling a mode does not establish insurance or legal sufficiency.
- Accountant-ready period reports and evidence: general ledger, trial balance, profit/loss, balance sheet, receivable/payable/customer-fund controls, reconciliation, invoices/receipts, mileage, asset register and corrections/export history. ACCOUNTING defines supported reports and reconciliation. Formal tax returns, tax advice, filing and automated depreciation are not promised; the tax preparer determines filing outputs. Prior-period records remain separately accessible for the tax preparer and are not erased by the fresh start.

## ADR36 - Exact-target provider-session reduction in the database

2026-10-23. Selected implementation design within the existing Phase2 session-recovery/revocation scope, following the owner's continuation. Synthetic implementation/testing is authorized; this is not permission for a hosted grant, maintenance login, production migration or activation. Retain Supabase Auth, password/TOTP verification, the standard Node application and all security/recovery gates. This explicitly extends the maintenance trust boundary; ordinary web/worker/recovery/inventory callers gain no provider-write authority.

Choose one fixed PostgreSQL definer operation, called by a separate nonlogin/noninheriting maintenance role, for the exact provider target derived from a schema23 cleanup request. Freshly validate its stopped finish, original signed target, immutable actor/epoch/source hashes and any revoked registration/reference under the schema22 producer lock. Provider deletion and immutable outcome capture share one transaction. Input is request ID plus expected actor/configured issuer, never an arbitrary provider UUID, token or broad user scope. Duplicate execution replays original evidence without repeating deletion. Outcome append failure/rollback restores provider rows and pinned cascades together. Bound provider-row waits and deny source conflicts.

The pinned Auth v2.197.0 implementation of local logout uses deletion of one session, with refresh-token and MFA-AMR child cascades. This adapter performs that narrow row reduction with an exact subject predicate; it does not emulate an HTTP logout response or insert a fabricated provider audit entry. Crest records its own immutable maintenance outcome. At migration and new execution, reject an unsupported provider migration watermark, ownership/RLS/table/key shape, changed/extra cascade dependencies, rules or user triggers. The isolated definer receives session ID/user-ID SELECT, session DELETE and the provider migration-version projection, plus safe Crest evidence reads/append. PostgreSQL17 MAINTAIN on only the two pinned child tables permits ROW EXCLUSIVE locks on all three provider tables before inspection through commit, fencing trigger/FK/schema DDL while allowing ordinary provider writers. This is the narrow available lock privilege without child secret SELECT or child INSERT/UPDATE/DELETE; its additional physical-maintenance capabilities remain confined to the fixed nonlogin definer and are not exposed through an API. No provider secret, user/factor write, UPDATE or application-role grant. The definer/caller are not service logins; provisioning remains a separate production gate requiring actual operator permission/support. An unsupported managed-provider permission/schema profile stays blocked and requires a reviewed supported alternative, not privilege bypass.

Alternatives: token escrow violates local revocation erasure; retrying an expired/missing token cannot prove cleanup; broad user logout harms other devices; forging tokens or retaining an administrative JWT is excluded. The official token-authenticated logout API remains the existing best-effort immediate path. A durable token-free database adapter is selected for this narrowly proven maintenance case, not a provider/runtime switch. Check current provider support/privileges before deployment; the pinned adapter must be reviewed/retested on every provider schema upgrade.

provider_removed records the exact transactional row removal. provider_absent_observed records a distinct point-in-time absence. Neither means all external I/O ended, all orphan sessions are gone or a still-unexpired signed JWT became cryptographically invalid. Crest's fresh provider/local checks remain mandatory; historical replay/lookup grants no fresh action or eligibility. Broader unknown/unfenced/legacy/enrollment cases, leases, bounded dispatch/telemetry, recovery/export and production grants remain gates. No scheduler/route/runtime adapter is activated. Tests must use the actual pinned provider schema, two-connection commit/rollback/row-lock races, injected outcome failure, cascade/source/grant drift, genuine Auth/refresh/MFA and another-device preservation. See planning/PHASE_2_PROVIDER_CLEANUP_EXECUTOR.md.
