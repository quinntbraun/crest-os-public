## 1. Model conventions that apply to every table

This is a logical implementation contract, not executable migrations. PRODUCT.md, BUSINESS_RULES.md and specialized ACCOUNTING.md 1.4 are normative. Every table below inherits these rules unless explicitly exempted; column lists describe required fields unless suffixed `?` (nullable).

- Primary key `id uuid`, generated as random UUID; never use customer name, phone, provider ID or invoice number as PK. Tenant-owned rows also have required `business_id uuid` FK and `UNIQUE(business_id,id)`. References between tenant rows use composite `(business_id,parent_id)` foreign keys. No cross-business FK can succeed.
- Provenance: `created_at timestamptz`, `created_by actor_id`, `origin` (manual/import/system), `operation_id uuid?`, `import_row_id?`. Actors reference a durable actor registry; identity deletion must not erase attribution. Tenant-owned actor association is validated. System actors are named and permission-scoped.
- Mutable aggregates: `version bigint >0`, `updated_at`; commands compare expected version. Append-only facts: no version update, correction uses `supersedes_id?` or reversal link. A projection may update only through its owning command.
- Default deletion is `RESTRICT`, not cascading. No ordinary runtime DELETE privilege on business history. Mutable directory records use `archived_at?`, `archive_reason?`, `duplicate_of_id?` with same-business FK, non-self check and cycle guard. Immutable commercial/financial facts cannot be archived out of reports. Hard-delete is limited to explicitly authorized unreferenced transient data and retention-policy procedure.
- Every FK has an index with `business_id` first except where an existing unique/index prefix covers it. Lists use stable `(business_id,created_at,id)` cursor ordering. Lookup/display search gets normalized phone/email/name indexes; these are not identity uniqueness constraints. Add pg_trgm only after measured search needs, not as a prerequisite.
- Enum-like business states are text plus CHECK constraints, not arbitrary strings. Migration changes their allowed set. JSONB snapshots carry a required schema version and validation; relational FKs and money never depend solely on JSON.
- Currency `char(3)` CHECK USD. Money `bigint` cents; all normal amounts nonnegative with explicit signed deltas only for event adjustments. SQL sums use sufficient precision; API uses integer strings. Percent/rate `numeric(12,8)`, discount fraction 0-1; tax rate nonnegative and profile-validated. No float conversion anywhere in postings.
- `timestamptz` stores UTC instants; `date` stores immutable effective/accounting dates; timezone text is validated against an IANA zone. Snapshot timezone on commercial/accounting/schedule records; never reinterpret history after settings change. Durations are integer seconds; distance/odometer `numeric(14,4)` miles, nonnegative, display at least hundredths. Geographic coordinates `numeric(10,7)` with latitude/longitude bounds and provenance. Local DST ambiguous times require selected offset; nonexistent local times rejected.
- Posted/issued snapshots retain names, addresses, vehicles, service/condition, provenance, rate/config versions and exact rendered customer-safe content as applicable. Current CRM FKs aid navigation; current rows are never the source of historic presentation.

Lifecycle codes in the table catalog: **M** mutable/versioned and archivable; **A** append-only retained; **F** draft mutable, frozen upon issue/posting; **P** replaceable derived projection with source events retained; **T** transient with explicit cleanup. All lifecycle classes are audited for meaningful changes. Routine job leases/heartbeat counters need operational history rather than a giant business audit entry every second.

## 7. Financial source model and accounting boundary

ACCOUNTING 1.4 sections 1-18, 24 and 26 supply the exact templates and semantic guards. These logical structures are required before dependent finance implementation; this document is not a migration. All tables inherit section 1's business-scoped composite FKs, durable actors, provenance, RESTRICT deletion and immutable posted payload. All monetary detail is cents/USD. Derived projections are rebuildable, never separate financial truth. Every financial command first holds the shared business recovery-authority lock, then finance_controls, and validates recovery_epoch, period, mappings, ancestry and chronology.

### 7.5 Transfers, reconciliation and periods

Transfers have stable source/destination channels, gross principal, fee expectation (unknown allowed), evidence and status projection. transfer_legs are append-only dispatch/arrival/return components with actual/effective dates, money movements, fee links and original leg references. transit_lots plus transit_movements track dispatched less arrived/returned principal, pinned1060, exact nonnegative remainder. Partial arrival and separate-date fee evidence cannot invent a balancing fee. Same-day confirmed two-leg transfer may post directly. Custody transfers consume named custody lots and create destination lots or actual business money; no sale/contribution.

statement_transactions are canonical provider/account/date/signed amount/state identities. statement_rows and statement_aliases retain raw import/batch/evidence versions; pending rows do not confirm money. reconciliations record account/interval/S0/S1/book B/generation/evidence hash/revision/status Draft/Reconciled/Needs Review/Qualified, approval, predecessor and invalidation. match_allocations reference canonical row/envelope and money movement with exact signed cents; active net revisions alone consume matching capacity across overlapping periods. Superseded match history is retained, not counted twice.

outstanding_timing_items reference an original money/opening movement, signed remaining cents, reason, expected clearance and immutable clearance_events with actual as-of date. Dedicated-account approval requires S1-S0=sum real statement rows and B=S1+O, all rows accounted for, zero unexplained difference and valid current generation. Exclusions are duplicate/nontransaction metadata only for business accounts; actual personal spending there is an owner event. Prior-period correction bridges are separate typed disclosure records, never fake timing items or clean earlier reconciliation. Corrections invalidate affected and balance-dependent successor approvals.

accounting_periods are nonoverlapping local calendar months (partial first month permitted), with lock projection and append-only lock/unlock/reclose events, report generation, close control snapshot, reconciliation IDs and exceptions. Qualified close can disclose omissions but never waive control equality. Recent authentication required to unlock. Reports include all originals/reversals by effective date and count opening journals once; earnings derived once, no mutable current-earnings balance.

### 7.6 Owner-custody model (ACCOUNTING section 26)

Required owner_custody_channels identify owner, masked personal account/cash arrangement, scope, pinned distinct1070-family asset control, reviewed cutover opening and evidence. They are business-only custody, not bank assets or loans. custody_lots and custody_movements track Crest-owned cents and provenance separately from customer funding roots (custody answers where held; funding roots answer customer entitlement). Fields include channel, event, evidence movement, contribution/receipt/transfer/supplier-refund/opening origin, selected input lot slices, output lot slices, custody debit/credit, funding shortfall split and disposition. Posted movement/source/journal equality per channel; each current lot nonnegative. Owner chooses named lots and amounts; UI may suggest FIFO by date/sequence but requires confirmation. No whole personal balance in this control.

owner_funding_splits bind each business outflow to custody cents, dedicated business cents or personal cents; sum equals business outflow and fee components. Personal funding requires explicit contribution or evidenced due-owner choice with typed contribution/obligation capacity links, never automatic negative custody. owner_settlements reference actual withdrawal/appropriation/transfer, selected custody lots or due-owner obligations, cents, reason/evidence; no unsupported netting, distributions never expense. Noncash ownership reclassification is explicitly labeled; no fictional bank movement.

`owner_contribution_lots` and `owner_contribution_movements` record owner, original typed funding source/cost ranges, immutable original cents, available/returned/converted exact slices, event and original consumption FK for restoration. Enforce ACCOUNTING26.3a conservation under finance lock; no repeated capital return/conversion with a different event kind. Corresponding owner obligations and settlements link these slices; changing a settled slice is not an ordinary funding correction. `unclassified_channel_evidence` stores channel, raw/normalized identity, amount/date/evidence, scope business/personal/unknown, reviewed allocation, pending funding election and resolution task. Unknown ownership never creates custody; coverage gates include this nonposting queue.

custody_reconciliations record channel, interval, prior approved business custody, event-derived closing, reviewed external business transaction IDs and signed amounts, verified included/excluded/unknown allocation decisions, outstanding items, coverage/evidence hash, owner completeness attestation and generation. Each included movement matches once; net evidence/custody bridge exact under section26; unknown business classification/coverage prevents clean approval. Excluded personal activity has no ledger entries. Full personal statement balances and unrelated transaction detail are not required or treated as business assets; retained excerpts must preserve relevant identity/amount/date and review evidence. Controls separately reconcile2350. Custody is never netted with due-owner in reports.

### 7.7 Legacy and recovery integrity

legacy_settlement_references store original customer/charge/service/tip/net/tax/discount, historical receipt identities and consumed capacities, remaining paid/refundable amounts, evidence and prior-coverage flag. They are nonposting, do not consume new commercial entitlement or invoice numbers, and exclude amounts already represented in opening AR/funds. A new legacy concession creates funds from legacy root; new legacy collection failure creates receivable_item. No historical cash/revenue replay.

invoice_series and invoice_number_reservations preserve full number, sequence, series, external-issue evidence, source or incident FK and tombstone. Unique business/full-number; reserve known lost-window numbers before reopening. Unknown high-water requires visible recovery series containing new recovery-epoch UUID; recovered issued numbers remain verbatim. recovery_authority_events record old/new epoch, incident, approver/time, preserved external log reference and reconstruction coverage. economic_identity_aliases bind recovered events to original source/provider/operation identities without second posting. Stale mutating commands fail even if operation absent; normal timeout retries remain unchanged-epoch only.

`recovery_reconstructions` and `reconstruction_dependencies` retain the incident-scoped fields and typed links required by EXPORTS_AND_BACKUPS 7.2, including evidence-proven original issue/effective/acceptance dates and separate new recording actor/time. Reservations have a unique optional reconstructed_invoice_id binding: only the proven matching invoice can claim an existing reservation. Original UUID absent means an explicit alias, never reuse of another entity identity. Recovery routines preserve every ordinary semantic guard and cannot trigger external sending/collection. Unknown required dependency facts block reconstruction.

Daily checks and every close/export/release reconcile ACCOUNTING C01-C22 plus custody controls by customer/root/item/account/effective boundary and ancestry. Unexplained overall ledger imbalance pauses all finance; localized mismatch pauses affected dependent domains. CRM/read/export remain usable with truthful warnings. No automatic repair journal.

## 10. Red-team schema guardrails

No generic cascade from customer/business/actor to historical facts. No `source_type + source_id` without a constrained typed source relationship for accounting.
