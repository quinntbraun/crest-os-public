## 1. Separate promises

Exports enable inspection and migration. Backups restore a compatible running system. Neither a report PDF nor a database-only dump is a complete recovery copy. Recovery objectives are <=24 hours lost committed state and <=24 hours recovery after incident declaration for the declared V1 capacity. They are tested service objectives, not a claim that arbitrary simultaneous provider/account failure cannot exceed them. An actual breach must be reported, not renamed successful.

Retain at least 30 daily and 12 month-end complete recovery points; extra six-hour checkpoints provide margin. Every retained point must retain all referenced original bytes and decryption/configuration material through the point's expiry. Photos/receipts are not subject to an independent lifecycle that can invalidate a retained point.

## 2. Consistent export protocol

Authenticated recent-reauthenticated owner requests an export specifying scope/filters. Queue record freezes parameters. Worker starts a READ ONLY REPEATABLE READ transaction, captures snapshot time, schema/version and reads every entity and control total through that same connection/snapshot. Streams with keyset cursors; do not release/reacquire a transaction per page. A watermark based only on updated_at is not a consistent snapshot of mutable/deleted rows.

Write private intermediate parts and verify checksums/counts before publishing one Ready manifest. Export never holds financial write locks. At <=15-minute snapshot duration, abandon incomplete output and retry or use a restricted restored snapshot for larger datasets. The latter is a new explicitly dated recovery-point export, not a silent substitute for the requested live snapshot; owner selects that as-of point. Do not combine parts across snapshots. Resource guard: one active full export/business and bounded worker memory; explicit progress. Failed jobs expose reason and retain source records; no silent truncation. A restarted export gets a new snapshot timestamp and generation ID.

All CSV/XLSX/PDF formats in one export job derive from the same captured rows/control totals, not independent later live queries. Worker's temporary data remains encrypted/private and is cleaned after upload. Attachment inventory is read from that snapshot; originals are immutable and protected against deletion while export is pinned. Unuploaded Pending evidence is listed as incomplete, not promised as downloadable bytes.

## 3. Portable formats

| Format | Contract |
|---|---|
| CSV | UTF-8, RFC4180 quoting, CRLF, stable snake_case headers; one entity per file, deterministic primary-key order; null literal `\N`, empty string retained as empty; escape literal backslash first as `\\`, then formula protection below; dictionary specifies reverse sequence |
| Scalar precision | UUIDs/text IDs retain exact spelling; bigints as exact decimal cents plus currency; fixed decimals as decimal strings; booleans true/false; date ISO YYYY-MM-DD; instant ISO UTC with Z; explicit original timezone/offset where relevant |
| Structured snapshots | Canonical versioned JSON in quoted CSV cell; documented schema; normalized children still exported separately for joins; no secret content |
| Spreadsheet injection | For text fields, after backslash escaping, prefix a single apostrophe if value starts with apostrophe or after leading whitespace/control characters starts =,+,-,@; schema records this reversible rule and escape indicator per affected column/row in companion escape map. Decoder removes exactly the indicated apostrophe then unescapes backslashes; never guess from appearance |
| XLSX | ExcelJS typed string cells for IDs, phones, raw text; typed date/amount analysis columns with exact cents text companion for values beyond safe spreadsheet precision; no untrusted formulas, external links or macros; Read Me, schema, filters, frozen headers, totals and coverage tabs |
| Workbook limits | Split before 1,048,576 sheet rows including header; use <=1,000,000 data rows/part; stable part naming and complete manifest. Oversized strings go to associated CSV/JSON evidence with explicit reference, never silent cell truncation |
| Financial PDFs | PDFKit templates; business name/logo if supplied, title, effective period/as-of, basis, USD/timezone, coverage warnings, generation time, page numbering and repeated headers; P&L, balance sheet, ledger, revenue, expense and mileage; source control totals printed |
| Attachments | Original bytes under stable `attachments/<attachment_uuid>/<object_uuid>.<safe_extension>` plus link table, original filename, type, SHA-256, byte count, capture/receive time, status and job/vehicle/expense references; no storage URL as sole representation |

A manifest is versioned JSON plus a human-readable README: schema version, app release, export job ID, snapshot time, business ID, filters, counts, control totals, currency/date conventions, null/escape rules, all part names/bytes/SHA-256, reference dictionary and attachment completeness. It contains no credentials, session hashes, signed URLs, private infrastructure endpoints or encryption keys. Stable actor identities/security-event metadata are exported; secrets are deliberately excluded and listed as such.

Required workbook tabs: trial balance, ledger, AR, invoices/items/credits, receipts/allocations/tips/funds/refunds, expenses/splits, mileage, reconciliations, controls and coverage. Operational workbook covers CRM/associations/leads/catalog/quote versions/jobs/appointments/custody/time/outreach. Full CSV includes all implemented business tables in DATABASE.md including archived/versioned/audit/configuration data. Reference-only historical records are separately labeled and cannot be mistaken for posted revenue.

V1 offers a batch download page and a documented resumable downloader protocol that fetches each original through authenticated endpoints, verifies length/checksum and retries missing parts. Owner obtains actual local bytes and manifest. Download authorization is rechecked per request; export expires after seven days and can be regenerated. No all-in-one archive ZIP feature is required. An offline verifier and a neutral PostgreSQL import exercise must reconstruct all relationships from these files without Supabase/R2 access. This round-trip test is a release gate, not merely a row-count demo.

## 4. Recovery architecture and credentials

Supabase Pro daily backups are a convenience recovery layer, not the BR17 system. Official documentation lists seven-day Pro daily retention and explains storage files are outside database backup coverage. Free is not an acceptable assumed production backup plan. PITR is optional future expenditure, not required for the specified RPO. See ARCHITECTURE S06/S13.

Chosen independent layer: Backblaze B2 account separate from app/database/object-storage administration, Object Lock compliance mode, encrypted backup artifacts using standard `age` tooling with recovery recipient public key. Private decryption key is held outside runtime in the owner emergency kit; two recoverable copies in distinct secure locations. Backup job has public encryption key only. Key rotation retains old private keys for every retained point. Use established formats/tools, not a custom encrypted database or repository format.

Separate runtime roles: backup reader (read-only complete app schema), primary-object reader (no mutation), vault append/list key without delete/retention-bypass, and a separate occasional retention administrator. Web/CI release process has no vault credentials or private decryption key. If provider capability does not permit the exact desired credential restriction, validate a narrower bucket/prefix and compliance lock before pilot; never substitute a master token. Audit Object Lock settings and attempt unauthorized delete as a test. Do not claim separate bucket alone is a separate failure boundary.

Backup scheduler runs isolated from the web service, using a pinned recovery-tool image. Hosting-account compromise can stop future backups but cannot delete already compliance-locked copies. Healthchecks account detects missed completed backups and alerts owner email independently. A scheduler heartbeat without a published verified backup does not count as success. Restore instructions and account/key recovery are also offline; they must not depend on the production dashboard being available.

## 5. Exact backup procedure

Every six hours (UTC 00:20/06:20/12:20/18:20), with retries and external deadline monitoring:

1. Acquire backup lease; verify connection, vault permissions, public key, free capacity and release/schema compatibility. Avoid round-hour scheduler congestion. Record start outside the production DB as well as locally.
2. Open REPEATABLE READ snapshot transaction; export the PostgreSQL snapshot and hold exporter connection open. Run pg_dump custom format against that snapshot, and read attachment/object inventory, counts and ledger control totals from that same snapshot. Direct/session-capable connection only. Include app schemas, sequences, routines, migrations and role/grant definitions through reviewed scripts. Do not dump only tables while omitting constraints/functions.
3. Copy each referenced immutable original not yet covered in the vault, stream SHA-256 and length, encrypt and record ciphertext checksum/key ID alongside protected plaintext checksum in encrypted manifest. Verify uploaded ciphertext and original source hash. A known object key is not enough; identify exact bytes/version. New objects committed after the snapshot belong to the next backup. Pending uploads at snapshot are metadata only and explicitly incomplete.
4. Snapshot can close after DB dump/inventory complete; immutable/no-delete original policy protects later copying. Publish no complete manifest until every committed retained original in that snapshot is retrievable and verified in vault, including Archived evidence and objects still referenced by historical versions. Available-only filtering is forbidden. Quarantined retained bytes are included in an isolated inventory and never rendered during restore. Derivatives can be regenerated; record versions and include any nonregenerable rendered acceptance evidence.
5. Include source commit/image digest, package lock, schema/migration hashes, database major/extensions, fonts/templates, object mapping, config export, recovery-tool versions, provisioning instructions and secret *references*. Keep an encrypted source/image recovery copy independent of GitHub/registry so account loss cannot make a two-year-old snapshot unusable. Auth users/memberships backed up with controlled procedure; auth sessions deliberately invalidated on restore. Supabase-managed auth schema restore is provider-specific and must be rehearsed; fallback reprovision owner and relink durable actor after verified identity, no business-FK rewrite.
6. Encrypt DB dump and manifest; upload immutable unique versioned names with retention. Verify archive readability/listing and checksum; publish final complete marker only after all checks. Then update backup_runs and send external success heartbeat containing run ID/time only.

Daily designated complete point retained >=35 days (safety margin above required30); last successful point at/before each local month end retained >=400 days to cover12 months. Use explicit local calendar boundary when selecting month-end; UTC schedule alone does not define it. Additional six-hour points retain seven days. Immutable original vault copies initially locked >=400 days; when a later retained point depends on an existing object, extend its retention through that point's expiry before marking success. If extension cannot be made with the restricted writer, copy to a newly locked version and point manifest to it. Never assume one original's initial lock covers all future monthly references. Retention administrator may collect only when no retained complete manifest refers to the object. At small V1 scale, keeping original backup copies indefinitely until approved lifecycle is simpler and safer than complex garbage collection; cost is monitored.

Any missing original makes that recovery point Failed, not partial Success. Preserve prior complete points. Verify decryptability with recovery key in restricted periodic restore, not by distributing private key to scheduler. Monitor key availability/recovery-kit checks independently; encryption without recoverable key is data loss.

## 6. Monitoring, capacity and recovery objectives

Expected six-hour checkpoints create retry margin before24 hours. Immediate error alert; warn at8 hours since last complete snapshot, critical at12, explicit BR17 breach at24. Dashboard reads last complete point age, object-coverage count, failed runs, retention inventory and last successful drill. External monitor separately watches absence of completed backup heartbeat and monitor delivery tests. Owner operational runbook requires response before deadline; no unattended scheduler can guarantee recovery under unbounded outages.

At the 12-hour critical alert, diagnose/retry or manually run independent backup. At 24 hours declare a BR17 recovery-objective breach, but CONTINUE ordinary financial entry, invoicing, receipts and other business writes per the owner's explicit decision on 2026-10-20. No new posting restriction is triggered solely by backup age. Show a persistent banner with the last complete point, unprotected interval and failure/retry state; send immediate failure and 8/12/24-hour escalation emails to the privately configured owner alert mailbox, then daily unresolved reminders with noise suppression. Acknowledging an alert never marks a backup successful. Show a recovery notification only after a complete verified run; preserve the incident history. External heartbeat must alert even when app/DB is unavailable. Freeze nonessential destructive migrations, retention changes and credential changes that would jeopardize recovery; security incident response remains allowed. Continuing writes increases potential loss beyond 24 hours if production fails before protection resumes; this is an explicitly accepted operational tradeoff, not compliance with the RPO. An unavailable DB cannot accept writes: show failure honestly, retain uncertain-operation identity, and reconcile field notes later without inventing offline success.

Growth validation profile (not yet tested, not the Free-tier launch entitlement): 10,000 customers,50,000 jobs,1 million journal lines,100 GB originals; expand with actual use. Two-year planning includes roughly70+ GB photo originals at the assumed rate, retained dumps and audit growth. RTO drill budget:2h access/provisioning,4h database/app restore,10h object download/check,4h financial reconciliation/smoke,4h contingency. These are acceptance budgets; measure real network and quotas, never assert timings from estimates. If drill exceeds24h, increase recovery resources/bandwidth or seek explicit BR17 change before growth passes capacity. Egress/retrieval, temporary compute and lock-retention costs are budgeted; no unlimited-free claim.

## 7. Restore and migration-disaster runbook

Before pilot, quarterly, and after material schema/storage/auth/encryption changes, restore a chosen point into a fresh isolated environment with outbound messaging/integrations disabled. At least annually restore a month-end point, recover using emergency kit and provision a neutral PostgreSQL instance plus S3-compatible objects to expose vendor lock-in.

Production recovery requires explicit incident-specific owner authorization and recent verified authentication or documented verified break-glass identity if app is down. Pause writes/jobs; capture current damaged state if possible. Select last trustworthy point (a newest backup can contain corruption), estimate loss window and enumerate later cash/quote/job evidence. Restore into new resources, never overwrite an active database. Restore schema/data and application compatible image first; load originals with hashes; revoke all prior app/provider sessions; rotate suspected credentials. Reconstruct owner auth safely before opening business data. Apply later migrations only after isolated compatibility tests.

Validate all FK/unique/check constraints and grants, row counts, accepted content fingerprints, quote allocations, invoice/funds subledgers, ledger balance/classification controls, openings, account reconciliation, original hashes/readability, current jobs/custody and basic mobile workflow. Missing objects, unreadable receipt or unexplained finance difference fails the drill. Preserve incident events externally to avoid the restored backup erasing the record of restoration itself.

Recover post-point records from provider statements, owner evidence and independent documents through reviewed imports with original external identities/operation IDs when available. Never replay a refund as a new outgoing payment automatically. Reconcile every later receipt and invoice number before reopening; reserve any externally issued later invoice numbers so they are not reused after restore. If evidence is insufficient, document unknowns and keep relevant books incomplete rather than invent balances. Only then switch DNS/app connections and resume operations. Retain previous resources read-only until incident closure, then clean recovery copies under approved process.

### 7.1 Finance authority and post-backup reconstruction

While writes remain paused, create a fresh UUID recovery_epoch, persist it in restored business recovery authority and the independent incident log, and revoke previous sessions. Reject every old-epoch mutating command, including operational commands and worker finalizations, under the transaction-held recovery-authority fence. Reject stale financial commands with RECOVERY_REVIEW_REQUIRED, including IDs absent in restored operations. An ordinary deployment or backup-age breach never rotates epoch. No automatic browser/worker resubmit under new epoch. Read-only old-operation lookup is permitted for review.

Reconstruct post-point activity using section7.2 incident reconstruction for proven lost records and normal typed late-recording commands for previously unrecorded events, retaining original source/provider/operation IDs as aliases. Recompute root/range/customer/AR/funds/custody/AP/tax/asset/prepaid/transit/suspense controls, exact ordering, openings, timing/match revisions and cost ancestry. Recover all known externally issued invoice full numbers as reservations before issuance. If high-water cannot be established, start an explicit visible recovery series containing the new epoch UUID; full number uniqueness spans all series. Recovered issued numbers remain verbatim. A new series only prevents number collision and does not clear a financial loss window.

Unknown financially material later activity blocks clean financial resumption. A bounded owner-approved qualified recovery may reopen only independently validated domains/accounts/items with incident coverage warnings; it cannot waive control equality or claim complete books. CRM/read/export may resume within verified security boundaries. Backup-age-only continuation remains unchanged. Preserve prior damaged state, old reservations and recovery evidence until authorized incident closure; do not treat the restored maximum sequence as external truth.

### 7.2 Reconstruction is not new issuance

First fence the former authority: stop/drain web and cron, revoke old write credentials or prove equivalent fencing, terminate old write sessions and invalidate restored sessions, upload attempts, worker leases and export download state. Rotate the single business recovery authority under its exclusive lock. Do not expose restored resources while old writers can still commit or publish referenced objects. Keep reconstruction incident-scoped while ordinary writes remain disabled.

Distinguish (a) a proven record committed/externally issued after the backup and subsequently lost, from (b) an actual economic event that was never recorded. Case (a) uses allowlisted recovery reconstruction, not an ordinary newly issued invoice. Preserve proven original business UUIDs where available, original full invoice number, source snapshots/hash, issue/acceptance/send/economic/effective dates, original actor attribution when evidenced, original operation/source/provider identities and known ordering. The reconstruction actor/time and incident are new immutable provenance; never pretend the database commit happened in the past. Unknown original actor/time/ID is explicitly unknown with retained external reference, not invented. Maintain old-to-reconstructed-ID aliases when the UUID is unavailable. Reconstruct missing agreement/completion/financial dependencies in topological order before dependents; no customer acceptance, fulfillment or tax facts may be fabricated. No external messages or money actions are triggered.

Normal invoice issue still uses actual current issue date. A recovery-only invoice may attach to its existing reservation for that exact externally issued number; atomically bind once under finance lock, without consuming another ordinary number or replacing an already reconstructed invoice. Prove original tax/mapping/component snapshots or keep reconstruction blocked. Unknown original order among dependent same-date events blocks affected reconstruction until evidence establishes it; independent events can use an explicit reviewed incident ordinal. Allocate new local commit sequences and retain original sequence as provenance when known. Original ordering is not falsely claimed from new insertion order.

Case (b) follows ordinary late-recording/correction rules and period gates; it cannot borrow case (a)'s historical-issuance exception. Reconstruction never silently unlocks a period. If required effective dates are locked, use explicit audited incident unlock/reclose, preserving previous approvals and invalidating dependent generations; do not move a known lost event to today's date merely to avoid a lock. Apply all existing typed-source, balance, range, ancestry and uniqueness checks to both cases. Reserve missing numbers before either path. Re-run chronology and all controls before approving each recovered domain. A qualified bounded reopen requires explicit validated scope, warnings and server-enforced blocks on unrecovered dependencies.

Export/backup `recovery_reconstructions` and dependency/identity aliases: incident, proven lost versus previously unrecorded classification, evidence hashes, original IDs/dates/number/actor/order with known/unknown flags, reconstructed IDs, approver, reconstruction timestamp, and applied policy. Portable reimport preserves these separately from current recording provenance. Restored in-progress tasks are reviewed/recreated with new authority, not blindly resumed.

## 10. P20 Calendar portability and post-restore reconciliation

Do not export Google tokens, OAuth codes/state, client secrets or private keys.
