## 1. Threat model and boundary

The realistic attackers/failures are a stolen unlocked phone, compromised email or hosting account, accidentally public storage/export, unsafe uploaded PDF/image, a dependency or SQL injection bug, and an engineering agent deploying an overprivileged migration. One owner does not eliminate these risks. Customer addresses/photos and money history are private; source code contains no production secrets or real test fixtures.

The browser talks only to the Next.js backend for business data. No browser Supabase table access, SQL access or service-role key. R2 staging uploads are the single narrowly signed exception. App, migration, backup and recovery credentials are separate. Tenant RLS is defense against query mistakes and accidental cross-business reads; it is not protection against a fully compromised application server holding its database credential. Independent immutable recovery limits destructive compromise; it cannot undo already-exfiltrated data.

## 2. Identity and sessions - D11 technical selection

Use Supabase Auth password verification and TOTP. Provision the owner's verified provider identity through controlled administration, then explicitly link its immutable subject ID to an active owner membership. Disable public signup, anonymous login and unused providers. No `email == owner_email` authorization and no first-login auto-owner. An unexpected provider user has zero business access even if authentication succeeds. Require TOTP enrollment before production; preserve emergency recovery materials securely outside the app. Passkeys optional later.

Authentication email uses custom SMTP with verified domain, SPF/DKIM and restricted redirect allowlist. Supabase's default SMTP is not a production recovery dependency. Password-reset responses are generic. Reset/reauth pages have no third-party scripts, analytics or arbitrary return URL. Provider identity and MFA behavior must be exercised with the deployed configuration. Official references: ARCHITECTURE S11/S14.

Implement a backend-for-frontend session using mature crypto/session libraries and provider SDK, not custom password or token crypto. Browser receives a 256-bit opaque random session cookie; database stores only its hash. Provider access/refresh tokens remain encrypted server-side with key IDs in app_sessions. Only backend performs refresh; lock session row for refresh rotation. Auth exchange uses provider-appropriate PKCE/state where applicable. Regenerate app session on login, privilege change and recovery.

Cookie: `__Host-crest_session`, Secure, HttpOnly, SameSite=Lax, Path=/, no Domain. Trusted session absolute maximum 30 days and inactivity maximum 7 days; untrusted absolute maximum 12 hours. Server timestamps govern, not cookie expiry. Background polling does not refresh inactivity; successful foreground protected interactions do. Recent-auth window 15 minutes for bulk export creation/download, auth/recovery change, period unlock and recovery authorization. New login or password+MFA reauthentication creates a fresh recent-auth assertion; ordinary token refresh does not.

Every protected request validates session not revoked/expired, live active membership, provider identity/session still valid and required permission. Validate provider JWT signature/issuer/audience/expiry and provider session existence; use a narrow nonexposed database function to check auth.sessions rather than grant app access to all provider auth tables. Provider timeouts alone are insufficient: Supabase documents enforcement at token refresh and JWT survival concerns. Application policy supplies exact max/inactivity/next-request revocation. Do not use provider single-session mode because phone and desktop must coexist.

Logout first revokes app session in DB, then requests provider signout; provider failure cannot restore app access. Lost-device control revokes selected app session/provider session; revoke-all bumps actor security epoch and revokes every session. Check epoch on each protected request with no cross-request authorization cache. Recovery/password change invalidates prior sessions. In-flight commands authorized before revocation can complete; revocation guarantees the next protected request, not rollback of work already committed. File streaming already begun cannot retract bytes; new download/range requests must reauthorize.

Recovery drill: lost phone but retained second factor; lost password with verified mail; lost both devices; compromised email; lost provider account. Provider administrative MFA reset is a documented break-glass process requiring owner identity verification and account recovery credentials outside the app. No unauthenticated "emergency owner" route. Provider migration may require credential reset/re-enrollment, but must not require rebuilding customer identities or audit actors.

## 3. Authorization and database roles

| Principal | Grants | Explicit prohibitions |
|---|---|---|
| Browser/anon/authenticated Supabase role | Auth endpoint access only | No app tables/functions/storage listing |
| Web runtime | RLS-filtered reads and allowlisted command execution; scoped staging-signing | No schema change, trigger disable, table owner, BYPASSRLS, journal/raw-history mutation or vault access |
| Command function owner | Only tables needed for the domain routines | Non-login, no superuser, no broad default PUBLIC execute; fixed search_path and schema-qualified SQL |
| Queue worker | Only task/report/file validation capabilities | Cannot post financial sources just because it runs server-side |
| Backup reader | Schema/data SELECT necessary for complete dump; no writes | Credential isolated from web; any required RLS bypass is read-only and explicit, not service-role reuse |
| Migration admin | Reviewed DDL/schema ownership in release job | Not a runtime secret; no unreviewed agent access to production |
| Recovery admin | Incident-scoped restore/reprovision | Not present in ordinary application environment |

Within a transaction, backend derives actor/business from verified session, sets transaction-local context and applies RLS. Roles and functions must reject absent/invalid context. Domain routines revalidate actor membership and business, expected versions and scope; security-definer functions must not rely on implicit owner bypass. Use fixed search_path excluding writable schemas, revoke PUBLIC execute and test direct routine abuse. Connection pool tests alternate tenants and rollbacks to detect context leakage. The service-role key is not the normal database connection.

Preserve actor/business/operator separately for future employees. Permissions use named capability checks (e.g., `finance.post`, `crm.manage`, `export.bulk`) mapped to owner in V1. No employee role UI, but avoid `isLoggedIn => all business powers` dispersed across routes. Every newly added route/function must declare capability and tenant ownership. File access checks parent record permissions, not only attachment ownership; a future field employee should not inherit receipt/ledger access through a shared customer.

Incident reconstruction capability is separate from ordinary finance.post and absent from queue/web general-purpose routes; it requires a current approved incident plan. Financial capabilities authorize only ACCOUNTING's typed source commands, including owner custody/settlements, original-range restoration, legacy adjustments, suspense resolution and close/reconciliation revisions. Every control line requires its source/schedule movement and independently checked ancestry. No owner/admin generic journal, imported account name, arbitrary debit/credit array or approved UI checkbox can bypass these checks. Used control-account role/mapping mutation is forbidden. Test direct routine abuse for every new subtype; preserve all existing RLS/grant restrictions.

## 4. Web protections and logs

- Mutations use POST/PATCH with same-origin Origin validation and synchronizer CSRF token bound to app session; deny unapproved CORS. SameSite is an extra layer, not the whole CSRF strategy. GET never posts finance, approves or accepts.
- Zod or equivalent boundary schemas reject unknown mutable fields, unsupported enum states, oversized bodies and malformed IDs. Parameterized SQL only; allowlisted sort/report columns. No string-built SQL from imports.
- Escape all customer/template text; no raw HTML from notes. CSP with nonce-based script policy, frame-ancestors none, no third-party scripts in protected screens. Sanitize any intentionally supported rich text (not required V1). HSTS after HTTPS verified; nosniff; referrer policy no-referrer for protected/link pages.
- No server fetch of arbitrary user URLs. Review links/directions allow https plus explicitly supported tel/sms schemes; do not proxy remote images or receipt URLs. Optional future fetchers require host allowlist, DNS/IP private-range checks, redirect validation and byte/time limits.
- Disable shared cache for protected SSR/API/exports; service worker only static assets. Browser/logout clears app-local draft state. PWA installation is not a security sandbox; device lock is necessary.
- Initial app rate limits: login 5 attempts/15 minutes per identifier and 20/IP; recovery 3/hour per identifier, generic result; ordinary mutations 120/minute/session; exports one running/business; uploads at most 3 concurrent/session and 100 starts/hour. Store counters durably with TTL and enforce provider limits too. Tune only with evidence; avoid permanent owner lockout.
- Operational logs: request/operation IDs, duration, route pattern, status/error code, release ID. Never log passwords, cookies, auth headers/tokens, request bodies, full email/phone/address, SQL parameter values, private image bytes, signed URLs or recovery material. Redact exception SDKs before transport. No session replay.
- Audit carries reconstructable business changes and necessary PII; it has the same access controls as source data and is included in protected backup/export. Do not put credentials in audit deltas. Sensitive reads (bulk export, financial report download, original file retrieval) generate access evidence without full URL secrets.

## 5. File security and declared limits

D11 technical limits: JPEG/PNG/HEIC photos <=25 MiB each, <=60 megapixels decoded; PDFs <=25 MiB and <=100 pages. CSV imports <=25 MiB/100,000 rows per reviewed batch, split larger input explicitly. No SVG, HTML, Office macros, arbitrary archives or video. Limits are versioned settings and tested on current phones; reject clearly before upload when possible. Never silently shrink an original receipt or damage photo to pass.

Use private staging, original and derivative prefixes/buckets. Sign upload for one random key, method and content type, 10-minute expiry; enforce size in server ticket and post-upload verification, not a claim that PUT URL itself reliably enforces every size limit. CORS restricts origins but is not authorization. After upload, worker streams bytes under hard size/decode/time limits, computes SHA-256 independently and validates magic/container/decoder. MIME/extension agreement alone is insufficient. HEIC decoder support must be proven on real iPhone samples before pilot; unsupported originals remain failed/quarantined with a safe JPEG re-export option, never falsely Available.

PDF processing runs isolated with memory/time bounds and no network. Reject encrypted/uninspectable or active-content PDFs (JavaScript, embedded attachments, launch actions); keep rejected bytes quarantined until reviewed under retention policy. Use a sandboxed raster preview for display; original PDF downloads use attachment disposition and nosniff. Patched open-source scanning supplements validation where practical; "scanned" is never a guarantee of harmlessness. No online public malware scanner receives customer files.

Finalization copies validated staging bytes to a fresh immutable original key and rechecks bytes/checksum before Available. Store final SHA-256/length and validation version. Lease/fence and conditional DB state update prevent a late validator changing newer attempts. Reusing the signed upload affects staging only. Originals have no overwrite route. Preview metadata/EXIF stripped for display; original EXIF remains private evidence. Capture timestamp is untrusted provenance, received timestamp server-authoritative.

Private original/preview/downloads go through an authenticated streaming proxy with fresh session/parent authorization on each request, including Range. Internal server-signed GETs may be short-lived but never returned as reusable public downloads. Upload tickets are the deliberate bearer exception; revocation prevents finalization and further grants, but an already-issued upload PUT may persist until its 10-minute expiry. Its bytes remain untrusted staging. This avoids promising instantaneous revocation of issued storage signatures. ARCHITECTURE S16 supports signed access capabilities; app policy is stricter for reads.

## 6. Public quote links - deferred but bounded

Required V1 uses manual sharing/acceptance; do not deploy a public-link route now. If optional feature is explicitly adopted: 256-bit random token stored hashed, exact revision/action scope, finite configurable expiry, server-side revocation checked on every view/action, no-store, no-referrer, no indexing/analytics/third-party assets. Token never appears in logs, metrics or exported URLs. GET may view customer-safe projection only; link scanners must never accept quotes. Acceptance requires deliberate POST confirmation, exact content hash and current-offer checks under family lock. Return generic unavailable for invalid/superseded/expired tokens.

Forwarding a bearer link grants its limited access. It is not proof of customer identity or signature. If identity assurance becomes required, amend the product contract before activation. Do not embed precise address or unrelated vehicle/history unless actually included in that approved customer projection. Revoking a link cannot erase a screenshot or downloaded quote; the user workflow must not imply it can.

## 7. Secrets, administration, retention and incidents

Store separate secrets per environment in platform secret stores. Backup encryption private key and vault administrator credentials must be recoverable from an offline/password-manager emergency kit inaccessible to app/CI runtime. Include key IDs and recovery instructions, never plaintext secrets, in manifests. Encrypt session-token column using maintained authenticated encryption, rotate with old key available until entries replaced; sessions may instead be invalidated on rotation. Do not create proprietary encryption formats.

GitHub main protected; lockfile and dependency review; CI actions pinned to commit SHA; runtime container non-root; image/SBOM/dependency/secret scan; production deploy credentials unavailable to fork/PR workflows. Only release workflow may access migration secret after gates. No auto-apply of untrusted generated SQL. Provider console accounts require MFA and independent recovery. Privileged break-glass actions get incident ticket, exported provider audit where available and manual signed action log where unavailable. Audit hashes are tamper evidence only; an administrator with all keys can still tamper. External immutable anchors reduce this risk.

D11 retention remains partly unresolved: no automatic deletion of customers, accepted quotes, finance, original evidence or business audit. This is a provisional preservation rule, not a legal retention conclusion. the owner must approve a legal/privacy retention schedule before destructive lifecycle automation. Transient cleanup is permitted only after proven unreferenced state: failed/staged upload bytes after 7 days, expired export output after 7 days (source remains regenerable), temporary worker scratch after task, redacted operational logs after 30 days if provider supports it. Retain minimal audit of cleanup and confirm no pinned export/backup/reference. Unknown referenced originals are never storage-cost cleanup candidates.

Incident sequence: revoke sessions/keys, pause affected mutations, preserve logs/current state, identify scope and trustworthy recovery points, rotate secrets, restore in isolated environment, reconcile post-point transactions, validate source/ledger/file integrity, then reopen. A suspected cross-customer leak is not solved merely by rotating a URL. Document exposure and seek appropriate advice for notifications; this architecture asserts no legal notification deadline.

Restore rotates a business recovery_epoch, distinct from the session security epoch, under incident authority before reopening. Every mutation and worker finalization validates it under the transaction-held recovery-authority lock before operation replay. Fence old runtime credentials/connections and drain or terminate in-flight writes; session next-request revocation alone is insufficient for restore. Revoke app/provider sessions as already required; session security epoch and business recovery epoch are separate controls. Old command epochs, financial or operational, fail RECOVERY_REVIEW_REQUIRED before replay/posting even if restored operation identity is absent. No browser, worker or routine may self-upgrade a stale command to the current epoch. Owner-reviewed reconstruction preserves original identities as aliases and known full invoice numbers; unknown high-water uses an explicit epoch-qualified series. Preserve the recovery authority record outside the restored database. Normal deployment and stale-backup alerts do not rotate it.

Mixed personal channel evidence is minimized to relevant business receipts, transfers, fees, refunds and settlement allocations. Do not request/store personal account credentials or ingest the entire personal balance as business data. Relevant original evidence and classification decisions remain protected, auditable and exportable; redaction cannot erase a business movement or break its identity. External review may examine a complete statement without making unrelated personal data a business ledger. Unknown scope blocks a clean custody reconciliation.

## 8. Security acceptance gates

Production D11 requires verified owner identity+TOTP, SMTP/recovery drill, device revocation on next request, exact timeout tests, cross-business denial including guessed objects/exports, no exposed app schema, role/RLS introspection, CSRF/XSS/injection tests, malicious uploads and signing races, safe logging, secret scan, isolated recovery and approved provisional retention handling. Funding/retention policy choices remain in ARCHITECTURE_DECISIONS.md. No production claim is made merely because these controls are documented.

## 9. P20 Google authorization and external disclosure

Google connection is separate optional consent, never a Crest sign-in/recovery path. Only a freshly authorized owner can initiate/change/disconnect it, with Origin/CSRF protections; a narrow state-bound OAuth callback is reviewed separately. Use a maintained server OAuth flow, one-use expiring session/actor/business-bound state, exact configured callback/issuer/client, account/scope validation and PKCE where proven supported; reject replay/account mix-up/changed sign-in. Keep OAuth codes/state out of logs, referrers and rendered errors; clean callback URLs. Encrypt integration tokens server-side with distinct purpose/key handling and serialized refresh; no browser persistence, CI or customer export secrets.

Request calendar.app.created rather than broad calendar/list/ACL access, with separately disclosed minimal OIDC identification if needed. Preview destination and generic event fields; client/service/address are separately opted-in, never financial/contact/vehicle/photo/internal evidence. No public calendar, bearer feed, guests, invitations, inherited reminders or ACL automation. Private visibility does not prove calendar sharing/device notifications are safe; owner sharing checks remain required. Disconnect fences/drains work before grant revocation; uncertain remote effects remain reviewable, and existing events are not claimed erased. Actual Google consent, client mode/policy, revoked/expired/partial access, leakage, restore fencing and real-device evidence gate activation. See ADR35 and GC01-GC18; no new permission or production access is enabled here.
