# Phase 2: isolated real Auth integration

This joins the existing provider/JWT boundary, schema4 narrow reader and local app-session prerequisites using the real pinned Auth server. No applied migration, canonical baseline, schema compatibility, hosted account, production configuration, real data or spending authorization changes. The application remains a closed setup shell.

## Recorded choices

npm run test:real-auth uses the same official Auth2.197.0 image digest already pinned in release/toolchain.json. The fixture records the empty bootstrap receipt, applies official provider migrations, then all unchanged Crest migrations. It starts the real Auth HTTP server against its owned disposable database. The container is non-root/read-only, capability-free, has a temporary scratch directory, no-new-privileges and Docker logging disabled. Host networking is required to reach the existing loopback PostgreSQL service; Auth binds only loopback on an ephemeral port. Cleanup removes only the container ID returned by successful creation and drops only explicitly owned fixtures.

An ephemeral test-only path bridge maps /auth/v1 to that local server and checks the generated test publishable-key marker. It never signs or rewrites provider tokens, users, factors or responses. It is not the managed Supabase gateway or production code; managed publishable-key/gateway/TLS behavior remains unproven. Admin API provisioning uses a JOSE-signed, RAM-only fixture service-role credential with the ephemeral signing key. Application requests use the existing official SDK boundary and real restricted runtime database login, never that administrator credential. No existing account/password/key is read. Private signing keys, passwords, tokens, TOTP seeds and codes stay in RAM or the disposable database/container environment, never files, Git, snapshots, artifacts or logs.

Public signup is disabled. Synthetic users are provisioned and confirmed through Auth's actual admin API; unconfirmed negative fixtures stay unconfirmed. TOTP seeds come from actual Auth enrollment URIs. OTPAuth9.5.2 generates real test codes using its maintained hashing dependency @noble/hashes2.4.0, both MIT and compatible with Node24.22.0. They are exact, development-only pins, reviewed against official npm metadata/source and installed with scripts disabled; no application password/TOTP crypto is implemented. Fixture challenge/sign-in/refresh rate limits are raised only to permit a dense deterministic test suite. This does not test or alter Crest's required durable login/CSRF/rate-limit policy, which remains downstream.

The production boundary now attempts SDK local-scope signout for a newly created session when the login ceremony fails. A fresh per-attempt SDK client owns only that attempt's provider session; no global/other-device signout endpoint is allowed. Success returns the existing server-only token handoff. The outbound allowlist adds only POST logout?scope=local and handles legitimate empty204 responses. Cleanup is best effort within existing deadlines: an outage/cancellation can leave an unexposed AAL1 provider session until provider cleanup. No credential or positive application access is returned on failure. The browser lifecycle must account for uncertain outcomes; this is not an absolute logout guarantee during provider failure.

## Required evidence and limits

Fourteen integration scenarios exercise public JWKS without private fields, disabled signup, real password/enrollment/TOTP and signed ES256 JWTs joined to the restricted reader and actual local session row, local revoke/security-epoch change, AAL1/no-factor/unconfirmed/wrong-password denial, incorrect code/factor/subject cleanup without revoking a valid device, sequential challenge replay, actual refresh-token rotation without renewed AMR authentication, two devices and local logout/rejected revoked refresh, administrative factor removal with a second verified factor still present, provider ban/deletion with durable actor retained, database-reader failure and Auth outage/recovery despite cached signing keys. No SDK, crypto, provider API or session reader is mocked in these tests. Isolated unit protocol tests remain complementary rather than replaced.

Local policy still yields only locally_eligible and provider verification only provider_verified. Neither is a business authorization decision. Real Auth HTTP integration does not provide a browser login route, pending-login store, encrypted token store, cookie/CSRF protection, durable rate limits, live tenant/capability context, recovery-authority command fence, enrollment/recovery UI or account-loss recovery. No simultaneous replay-race guarantee, key rotation/restore, hosted deployment, production TLS/credential/configuration or free production reliability proof is claimed. Those remain explicit release prerequisites. All existing real-data/recovery/financial activation gates remain closed. Current spend remains$0.

Full Linux CI must pass the new suite plus existing lint/types/unit, real database, dependency/audit/secret/provenance, production build, browser/axe and non-root container gates at the exact reviewed head. Windows compiler/Docker limits still apply. CI evidence belongs in the PR before a protected merge; review is by the implementing assistant, not independent certification.
