## Schema21 and authority

provider_login_targets is an append-only forced-RLS table linked to the immutable schema20 header. It retains the pinned actor/epoch/issuer/subject, provider UUID, signed password/expiry reference times, database-derived creation time/principal, schema1/origin system and original JSON text/SHA256. The invoker insert trigger matches header identities and password time at/after the header's database second and not in the future, rejects first adoption of an existing app/provider registration, and replaces supplied body/hash/provenance/time. Only the trusted server verifies the JWT; PostgreSQL validates the reported reference relationships, not its provider signature. The stored SHA256 is a portable content checksum, not an independent signature or attestation. One target per attempt and one attempt per issuer/provider-session pair. No reference backfill is invented for older attempts or sessions.

record_provider_login_target is a fixed session-owner definer. A domain-separated nonwaiting transaction advisory lock serializes each attempt. Exact typed replay returns the original JSON bytes/hash; changed input conflicts; an overlapping call returns busy; rollback or insertion failure leaves no partial receipt. This evidence-only replay grants no login retry or authorization. A late verified reference remains recordable after epoch change, owner disable or provider disappearance: rejecting historical evidence would hide the very uncertain sessions that need later review. It does not upgrade the old epoch, restore authority or make the provider session live. Initial password time still has to match the original start window; provider expiry is historical metadata, not a current-eligibility decision.

issue_targeted_app_session requires the exact retained target/password time, then invokes schema20 tracked issuance and schema6's current root/membership/epoch/live-AAL2/fresh-authentication checks. Legacy issue_app_session and issue_tracked_app_session remain compatible for earlier runtimes; no claim that all historical/enrollment/direct SDK paths are covered.

The isolated inventory definer gets SELECT on the new safe table only; no new roles, memberships or source privileges. provider_login_target_inventory exposes bounded1..100 UUID-keyset pages under exact actor/issuer. Unregistered targets are registration_unconfirmed; exact target/actor/epoch/immutable CREATED operation is registration_recorded; mismatched app/source identity is binding_conflict_review and does not expose that conflicting app's revocation. The target UUID itself is retained historical evidence and remains visible in its own receipt. Local refresh/revocation or provider deletion cannot erase its historical association. No outcome, expiry-driven close, orphan/absence proof, complete cross-page snapshot or cleanup action is inferred; inserts behind a cursor require a new sweep. No administrative secrets, raw tokens, provider DML, current-user cache or ordinary browser inventory access.
