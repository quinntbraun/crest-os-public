## Decisions

SECURITY4 specifies5 login attempts per15 minutes per identifier and20 per IP. Each admitted attempt is durably reserved before future provider I/O, regardless of eventual authentication success. Rejected requests append no row and do not extend lockout. A rolling timestamp range avoids a fixed-window boundary burst. Database time controls the window; attempts at or before now-minus15-minutes are expired. Counting checks both indexes under one short singleton row lock in READ COMMITTED. Concurrent app processes share the same decision, and new adapters/restarts retain admitted history. The transaction ends before any provider call. No credentials, provider tokens or request bodies belong in these operational tables.

A single operational root deliberately serializes this low-volume internal login admission rather than creating unbounded per-identifier lock rows or adding a cache service. Runtime statement/lock/query/connection-operation bounds remain1.5s/750ms/2s/3s, with1s connection establishment. Contention, database outage, privileged/broadened runtime credentials and cancellation fail closed. An uncertain commit may consume an attempt; callers must not assume it rolled back or automatically refund/replay it. This availability tradeoff must be measured before any public/multi-location scale claim.

The server supplies a separate random32-byte HMAC key, stable across processes and restarts, and a trusted literal client IP. Node's maintained HMAC-SHA256 hashes domain-separated normalized identifier and IP values. Identifier normalization trims outer whitespace and lowercases only for conservative rate grouping; it never links an actor or establishes ownership. IPv6 spellings normalize through Node URL serialization, and IPv4-mapped IPv6 groups with IPv4. Hostnames, address:port strings, forwarding chains, zone IDs and missing addresses deny. These functions never trust a browser-provided forwarding header. A future deployed ingress must explicitly establish its proxy/IP trust boundary; blindly trusting X-Forwarded-For is prohibited.

The database stores only keyed identifier/IP fingerprints and admission timestamps. The first committed admission binds the separate key fingerprint atomically; rollback leaves neither binding nor attempt. A different key returns denial rather than silently creating another counter namespace. The key itself never enters SQL, logs or source control. The fingerprint is not an authentication secret. There is no runtime key-reset command. Key replacement requires coordinated, reviewed privileged maintenance with admissions paused for at least the complete15-minute window; restore/configuration drills must retain or intentionally reconcile this operational state before reopening login. A missing/wrong key is an availability failure requiring operator repair, never a bypass.

Operational rows have a logical15-minute TTL and lazy physical cleanup of at most256 expired rows per valid-key request. Expired rows never count even if cleanup has a backlog. No requests means physical deletion may wait; this is not a guaranteed15-minute physical purge. A future operational worker/retention runbook must address scheduled cleanup and retained backups before production. Denied requests create no per-identifier key rows. Recovery/ordinary-mutation/upload/export limits have separate policies and are not implemented by this login-only command.

The new crest_login_owner is NOLOGIN/NOINHERIT/non-admin/non-bypass with no memberships or schema CREATE. It owns only fixed pg_catalog,pg_temp-path row_security=on admit_login. Forced-RLS private operational tables remain owned by crest_schema_owner. The closed owner can select operational rows, bind the singleton key once, insert admissions and delete only expired rows; it cannot update attempts or read sessions, memberships, business data or provider tables. A trigger prevents rebinding an initialized key. Web has EXECUTE only and no direct table access. Migration preflight rejects unsafe role attributes/memberships and writable-schema drift. These anonymous operational records deliberately have no business actor or domain audit identity; they are not financial/history tables.

The independent mutation guard accepts only POST/PATCH JSON from an exact configured Origin and, when supplied, Sec-Fetch-Site:same-origin. Missing/null/multiple/foreign origins deny; referer, Host and forwarded hosts never replace the configured origin. No CORS allowance is added. Production configuration requires HTTPS; literal loopback HTTP is explicitly test-only.

Synchronizer tokens use Node randomBytes32 and SHA256 with a session-UUID/domain binding. The server explicitly stores the defensive32-byte hash and sends only the random token through the deliberate response handoff. Verification uses timingSafeEqual and the current trusted session ID/hash, requiring the token in X-Crest-CSRF. Wrong-session substitution, noncanonical base64url and missing/duplicate tokens deny. Token objects block accidental JSON serialization. These are server primitives, not a claim of complete CSRF protection: the schema does not yet store per-session CSRF hashes and no route invokes this guard. Pending-login binding, transactional storage/rotation, response no-store headers, cookie handling, nonce CSP, request size/schema validation and full browser-flow tests must be completed together before enabling browser login or protected mutations. SameSite alone will not substitute for synchronizer state.
