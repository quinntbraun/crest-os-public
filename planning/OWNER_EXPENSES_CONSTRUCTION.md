# Owner expense construction

This branch adds manual paid-expense entry, corrections, voids, retained history and an accountant CSV handoff over registered45. It is an unregistered, disabled construction, awaiting the native integration owner's migration and recovery adoption. No real business records, provider accounts or payment movements were used.

## Scope reconciliation

The owner's October28 instruction prioritizes a reliable single-owner operating tool over a sellable SaaS product. The owner then accepted invoices, manual payment tracking, expenses and income/expense reporting while a tax preparer handles formal books. This construction follows that later instruction rather than claiming completion of the earlier full-ledger plan. It is owner-entered cash bookkeeping, not certified accounting or QuickBooks feature parity. Invoices, payments and balances remain with the native integration owner; appointment proposals, Calendar preparation, follow-ups and customer duplicate review remain with the cloud owner.

This slice records positive paid expenses in USD, dated by the owner. Categories organize the records and do not determine tax deductibility. Refunds, tax accounting, mileage, bank reconciliation and a general ledger are not implemented here. Each save has a stable operation ID, a pinned recovery epoch and an expected revision. Corrections require a reason; voids preserve the preceding financial content and retain their reason. Voids cannot be silently reopened. Same-amount payments are not automatically deduplicated because separate purchases may legitimately match.

## Delivered construction

- `planning/proposals/owner-expenses.sql`: one forced-RLS immutable revision table, closed nonlogin command role, financial mutation fence, shared operation claims, retained audit images and commit-time integrity checks. The existing authentication routines are pinned before grants. Existing migrations are unchanged.
- `src/bookkeeping/expenses/`: closed domain validation, exact-cents conversion, server directory and disabled HTTP handler, safe accountant CSV plus JSON totals/escape notes.
- `src/client/expenses.ts`: private POST transport, bounded replies and session-bound edit context. History is obtained in one bounded database statement rather than mixing independently paged snapshots. Construction limit:1000 retained revisions or6MiB of history. Reaching it fails visibly, without truncating an export.
- `src/app/expenses/expense-editor.tsx`: mobile form, retained history, corrections/voids, interrupted-save lock and same-operation retry, original-operation discovery in retained history, payment-date export selection. Unsaved entries and unconfirmed saves stay in memory and warn before navigation; there is no automatic offline write queue.
- Focused unit, PostgreSQL, genuine local Auth/TOTP/restricted-login HTTP, and supplemental Chromium/WebKit component checks. The UI-only adapter is explicit and is not persistence or authentication evidence.

The CSV includes all retained revisions of expenses whose latest payment date falls in the selected period. Export refreshes saved records before formatting, including changes from another device; unsaved form edits stay separate. A failed refresh does not produce a stale download. Totals use only latest nonvoid rows. `is_current` identifies the current revision; separate `reportable_amount_cents` and `reportable_amount_usd` columns contribute zero for superseded/void rows so summing them does not double-count corrections. Original amounts remain in separate history columns. Formula-like text receives an apostrophe with a precise row/column escape map. These private downloads do not include receipt bytes or establish complete source-export/backup custody. They are an expense handoff, not a profit report. The owner must download both the CSV and accompanying notes; browsers may require allowing multiple downloads.

## Private receipt follow-up

`owner-expense-receipts.sql` adds an immutable forced-RLS reservation/publication history bound to a retained expense revision. It reuses the expense command role and generic operation/audit records; all five expense routine bodies, owners and settings are pinned before grants. Receipt reservation uses `finance.post`, the original recovery epoch, exact expense version and stable staging/original/preview/dispatch identities. The reserved original and preview keys never change on retry. Publication is refused for a voided expense or paused/restored epoch. Earlier states and receipts of subsequently voided expenses are retained.

The SDK adapter reuses the existing private create-only storage mechanics and validated intake. A lost PUT response or existing candidate is reconciled by bounded GET, exact byte count, declared type and SHA256; it never repeats a durable PUT, trusts an ETag, overwrites an original, deletes bytes or rotates a key to hide uncertainty. Candidate metadata comes only from the trusted dispatcher. Ordinary authenticated downloads need no decoder capability, verify bytes against retained metadata and freshly reauthorize after the storage wait. Responses are private attachments with fixed UUID-based names, `no-store`, `nosniff` and a sandbox CSP. Public JSON views exclude canonical object keys; upload capabilities are an explicit short-lived, staging-only handoff.

The receipt HTTP construction is explicitly test-only and disabled by default. It requires an operator-supplied **isolated dispatcher transport**. Do not hand the ordinary web process a Docker socket. `createLocalSandboxValidator` remains Linux-only; Windows tests do not bypass that guard. The client and receipt panel now support file selection, stable-ID retry, saved receipt lists and private original/preview downloads. They are an optional composition of the expense editor, not a new public page or an enabled runtime route. Provider bucket CORS and an independently verified worker deployment are still prerequisites for real browser uploads.

Receipt source formatting validates every supplied receipt-to-expense revision reference and preserves reservation/publication history. File names match the separate private downloads. The recovery inventory includes receipts of corrected/voided expenses and refuses pending reservations rather than silently discarding unknown candidate bytes. The actual `age` archive component restores originals/previews with an emergency key after source/original-key removal. The genuine-MFA HTTP/SDK pipeline also feeds retained database metadata into this export/archive path. Its validator is an explicit protocol seam, so that case is not a decoder proof. No formatter or component test establishes complete held-snapshot database recovery, real R2/B2 custody, Windows owner-only key ACLs or independent-account access.

## Lifecycle and binary transport correction

Independent review of accepted source8bfcc341 found deferred CSV/notes and receipt downloads could finish after their component unmounted. Both components now fence asynchronous results to their mounted generation and source scope before state updates, Blob URLs or download clicks. The receipt client also checks the caller's lifetime predicate before creating a Blob, including after hashing. Actual Chromium/WebKit regression cases exercise unmount and source replacement, with mounted positive controls proving normal CSV/notes and receipt downloads still occur. These remain explicit UI-only clients, not authenticated persistence proof.

The old receipt HTTP fixture bypassed the Node transport and therefore missed its inherited customer writer's1MiB limit. `receipt-download-response.ts` now supplies a one-use branded receipt binary response and separately bounded socket writer: validated originals up to25MiB, JPEG previews up to8MiB, exact length/hash, fixed private attachment names/headers, refusal of altered/consumed/unbranded responses and transport-buffer wiping. Ordinary JSON/customer limits remain unchanged. The genuine-MFA receipt/SDK/archive fixture now sends an original larger than1MiB through the actual adapter; a separate real-socket case exercises the full25MiB boundary.

During native49 routing, use `isReceiptDownloadResponse(response)` to select `writeReceiptDownloadResponse`; small receipt metadata/errors retain the existing bounded JSON writer. Do not send binary receipts through `writeCustomerResponse`, raise all generic response limits, or expose a raw object-store URL. This branch adds no shared router edits or preview activation. The new correction requires its own exact-source acceptance;8bfcc341's earlier full success does not accept these new bytes.
