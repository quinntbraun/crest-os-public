# Verified browser download transport

2026-10-27. Local construction after published foreground sourced8963b69/run40483921415, which has independently bound1,252 database/Auth passes. Its full release is a separate prerequisite; preserve the healthy parent run before publishing this client. No product page/route activation or canonical43 adoption is included.

The new stateless client uses the existing HttpOnly-session/CSRF endpoints at fixed same-origin POST paths. It copies strict requests, expected evidence and expiring proof before asynchronous work, disables cache/redirect/referrer use, bounds catalogue JSON to16KiB/128nodes and rejects duplicate keys. The first catalogue page has no generation pin; subsequent pages require the exact original12-field header and generation. A page is metadata, never reusable download authority. The server freshly checks current owner/recovery authority on every file request.

For a file, the client requests only job/generation/part IDs and requires the exact200 attachment MIME/name/length/checksum plus private/no-store/no-transform headers and no content encoding. It accepts one bounded whole part, at most8MiB, and computes its actual SHA-256 using built-in WebCrypto before calling the consumer. Partial, oversized, truncated, corrupt, redirected, changed or expired responses never reach the consumer. Limits stay unchanged. Rate limiting is explicit; the transport never retries, polls or clears an original pending operation.

Only one download per client may own a plaintext buffer. Cancellation and deadlines bound fetch, stream reads, crypto and consumer work; late responses are cancelled. Its allocated byte buffer is cleared in finally after success/failure/cancellation, including a stalled or failed consumer. This is an owned JavaScript-buffer guarantee, not a promise to overwrite immutable browser strings, internal fetch/crypto buffers or copies a save callback creates. The client creates no Blob, download URL, disk file or persistent state. The callback must finish using the bytes before resolving; a caller must abort on current-principal/context/lifecycle changes.

## Whole-file resume contract

A batch consumer first reads the current catalogue, pins the validated header and obtains all descriptor pages with that same header. Before claiming a complete inventory, it must additionally check global name/part uniqueness, contiguous ordinals, exact counts/byte totals and manifest closure; the stateless page transport does not claim that aggregate proof. To resume, compare actual local files with these descriptors by exact name, byte count and SHA-256, then request only missing/invalid parts with fresh session proof. Restarting a part is explicit and whole-file; no byte Range protocol or all-in-one ZIP is required. An expired or regenerated job must start a separate generation and cannot be silently mixed with old files.

Receiving verified bytes proves neither OS persistence nor a completed batch. A Blob/link save can only be described as prepared/requested until local bytes are checked. The batch UI and local-file verification are still to implement; no saved-file or complete portable-export/backup claim follows from this transport.
