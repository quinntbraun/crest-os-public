## Decision and behavior

Schema20 adds an append-only forced-RLS provider_login_attempts header. Before any password/TOTP provider I/O, the server validates and snapshots its input, reserves an attempt UUID and future app-session UUID, resolves the exact configured issuer/durable subject, and confirms a committed begin_provider_login result. Actor ID and security epoch are pinned before I/O. Failed, cancelled, malformed or uncertain begin results stop the provider call without replay. An epoch change during the exchange requires a fresh login; it cannot rebase the old attempt.

Headers retain schema1/origin system, actor/epoch/issuer/subject, both UUIDs, database-derived UTC creation time/principal and original canonical JSON text/SHA256. They contain no email, IP, credentials, codes, tokens or encryption metadata. The invoker insert trigger validates current owner binding/epoch, locks the actor, rejects existing app UUID adoption, and discards supplied body/hash/provenance/time. UPDATE/DELETE/TRUNCATE are rejected. Duplicate attempt/reservation is an error, never a grant to repeat a password exchange. No automatic expiry, close, resolution or provider identity is inferred from a start marker.

The current server lifecycle issues through issue_tracked_app_session. It requires all reserved identities and the exact original epoch/attempt, then invokes the existing live provider/current owner/membership/root-lock issuance boundary. The immutable CREATED event operation_id equals the attempt UUID. Registration cannot release an opaque credential until the existing final local/provider checks pass; existing scoped best-effort cleanup remains. Ordinary admission/CSRF/origin/rate boundaries still precede the lifecycle.

A separate maintenance-only provider_login_attempt_inventory returns1..100 ordered UUID-keyset headers scoped to actor/exact issuer. No app row means registration_unconfirmed. Exact actor/epoch plus immutable CREATED operation association means registration_recorded, including after current operation changes, revocation or provider disappearance. A reserved UUID with conflicting binding/source is binding_conflict_review and hides provider/revocation fields. These are historical registration facts, never current session eligibility, complete provider enumeration, safe orphan proof or cleanup authority. The existing inventory definer gains only SELECT(id,session_id,actor_id,operation_id,action) on source session_events with explicit RLS; no payload read or event DML. No new roles, memberships, login provisioning, administrative secrets or provider writes.

## Compatibility and remaining gates

Original19 SQL and12 canonical amendments are unchanged. App0.1.0/schema0..20/report0/command1; forward-only coordinator, reviewed privilege/configuration checks and pending-review behavior apply. Legacy untracked issuance remains executable for earlier app compatibility, and retained pre20 sessions receive no invented markers. Direct provider SDK enrollment/test calls and older app versions are outside this current lifecycle. A recorded registration does not prove no other unknown provider sessions were created by that attempt. Provider loss after a successful exchange and before storage remains uncertain.

No process lease, terminal attempt outcomes, worker consumer, safe automatic classification/closure, targeted remote cleanup authority, token-free expired-token cleanup mechanism, retention/telemetry or UI is implemented here. Header retention is deliberately unbounded pending the bounded maintenance/recovery design. No production activation, real records, owner signup, spending or deployment.
