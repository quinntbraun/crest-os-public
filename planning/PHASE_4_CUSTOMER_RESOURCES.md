# Customer vehicles, addresses and associations

Work in progress after the real customer source in PR67. This is the next part of the synthetic CRM milestone, not completed vehicle/address workflows or production permission. Preserve every published migration and original canonical document. No category, lead, job, quote or file parent is fabricated. Existing DATABASE/BR02/P03 requirements govern implementation.

Payload contracts retain label-only vehicles, optional year/make/model/color/VIN/plate and raw notes. VIN normalization is only an ASCII alphanumeric uppercase search hint; shared or unusual input never creates identity, deduplication or a uniqueness constraint. Year uses PostgreSQL INTEGER representability, not a current-year plausibility prohibition. Unusual years remain recordable with later UI warnings. Vehicle kinds are the three existing canonical values. A genuine category relationship requires the catalog workflow; it is not represented by a fake ID here.

Customer addresses may remain incomplete at intake. Preserve structured raw/null/empty fields, exact location text/instructions and optional paired coordinates. Decimal strings go to PostgreSQL NUMERIC without JavaScript Number conversion, rounding, exponent notation or latitude/longitude boundary loss. Explicit geocode metadata and verification remain independent facts; do not infer them or overwrite an owner-entered address. Future scheduling must require an exact confirmed work location. The customer-owned workflow precedes lead-owned address links; no missing lead table/seed is fabricated.

Customer/vehicle association creation requires genuine IDs, explicit effective UTC instant, owner/keeper role and optional evidence. Closing is a distinct audited action with explicit end/reason; it must not rewrite the start/customer/vehicle. Database commands must enforce same-business parents, end>=start, one current billing association per vehicle and exclusion of overlapping owner periods, including concurrent creation/transfer. Transfer must close/open atomically with stable operations and original recovery authority. Original job/customer/photo/commercial snapshots must remain untouched by current directory changes.

The first source implementation is the [customer-owned address backend](PHASE_4_CUSTOMER_ADDRESSES.md) in migration34: restricted owners/RLS, complete audit, stable receipts, parent/version conflicts, typed server adapter,26-column snapshot/CSV and an actual encrypted recovery fixture. Native execution remains required; local tests do not prove PostgreSQL behavior. Vehicle and association input contracts remain initial work only. Implement their genuine source/command/concurrency/history/export/recovery and private forms next; no fake category/lead parent, untested migration apply or production claim. Private address HTTP/forms now consume that backend under the same explicit customer opt-in; native current-source acceptance is required. No geocoder, spending, real data or default activation.
