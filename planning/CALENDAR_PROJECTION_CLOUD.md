## Delivered code and boundaries

`validateAppointmentWindow` validates stored UTC instants against original IANA zone, local calendar date/time and separately reviewed offsets at both endpoints. A fold requires an explicit matching UTC/offset pair; a gap cannot roundtrip. Invalid dates, end-before-start, missing end times, sub-millisecond precision, numeric-offset zone identifiers and mismatched local/UTC/offset facts are refused. Input precision is seconds or milliseconds and offsets are integer minutes. The validator uses the executing runtime's ICU timezone data; staging/Google/real-phone comparison and runtime data-version evidence remain required. It does not select a local-time ambiguity for the owner or implement a scheduling source/confirmation workflow.

`buildCalendarEventProjection` constructs a frozen, versioned payload preview. Default fields contain a generic label, opaque job reference, reviewed times/zone and a trusted-application job URL. Each of client display name, service label and work address requires an individual explicit selection. The builder creates a fresh allowlisted object and refuses unknown source/consent fields; it never spreads customer, financial, contact, vehicle or credential records. HTML-capable service description text is escaped. Selected display strings reject controls, bidi/format characters and unpaired surrogates with redacted diagnostics. Emoji without format characters and international text are supported; richer format-character text needs a separately reviewed rule, not silent normalization.

The mapping UUID becomes lowercase hex and stays independent of appointment version/consent. The caller must create and retain one mapping identity per job/destination; the builder does not allocate, persist or prove its uniqueness. Private visibility and disabled inherited/override reminders are explicit. No attendees, invitations, conference data, attachment payload or provider request is constructed. Clearing disclosure returns replacement managed values, including empty location, so a future reviewed update can remove old shared text. That update must first check external guests/edits and etag; this builder grants no overwrite permission.

The generated `/jobs/{opaque-reference}` URL is a **future** authenticated job destination, not an implemented route or access grant. No such link is published here. Trusted runtime integration must bind this to an actual authenticated job route before provider acceptance. Likewise, the `confirmed`/`completed` input is not database evidence: a future trusted source adapter must obtain committed confirmation and retained appointment/version/consent/mapping facts itself. A completed source projects the same appointment; this module never decides to insert another booking. Draft/proposed/cancelled inputs are refused. Cancellation/removal is a separate future protocol, not inferred from a refusal.

This is preparatory pure code under P20/BR21/ADR35, not completion or activation of Phase6 or P20. Canonical scheduling/outbox, provider/maintenance/recovery and all release prerequisites remain unchanged. No schema, canonical document/provenance, published migration, dependency/lockfile, CI, authentication, quote writer, runtime composition or production change is included. No signup, credential, cost, account connection or transmission is introduced.
