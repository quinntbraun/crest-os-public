## PostgreSQL17 commit-role correction

PostgreSQL17 executes deferred invoker triggers using the role active when they fire, which can differ from the role inside an earlier security-definer writer. The PostgreSQL18 change to capture the initiating role was explicitly not backpatched. Therefore the schema13 admin-only storage tests were insufficient evidence for a future restricted web transaction committing after a definer returns. Preserve those historical tests at13 and add a before/after reproduction on the actual pinned PostgreSQL17 image. Do not upgrade PostgreSQL, weaken web grants, force checks early, or alter constraint timing to hide this boundary.

Schema14 assigns only check_identity_roots and check_operation_completion to a new crest_integrity_owner nonlogin/noninheriting role, marks them SECURITY DEFINER with the existing fixed search path plus row_security=on, and revokes PUBLIC execution. Their bodies, checks and deferred timing are unchanged. No role membership, superuser, BYPASSRLS, schema CREATE or runtime ability to assume this role is added. An existing cluster role must be pristine with no target-data privileges/default-grant/config/membership drift; reject drift rather than repair it. This matches the existing cluster-role migration model. Test sandbox ownership/cleanup tracks the ninth role.

The checker receives only required columns: business IDs, membership business/actor/active/role, actor ID/kind/disabled flag, recovery-root ID/business, operation business/ID/actor/state and audit business/operation/actor. Its forced-RLS SELECT policies span these invariant inputs because commit correctness cannot depend on whichever request GUC is active then. It cannot read provider credentials, sessions, names, result/digest bodies, audit deltas/hash inputs or active recovery epochs. A lock-only business.id UPDATE grant has false WITH CHECK, as in the existing session-owner lock policy; no actual data update is permitted. Trigger functions are not callable RPC readers and web has no EXECUTE or TRIGGER/schema permissions to repurpose them. The role is an invariant checker, not an application/backup principal or an authentication bypass.

## Narrow operation reader

Schema14 adds authorize_business_operation_lookup owned by the existing session owner. It calls the established exact SDK-binding/local/provider/membership/root read guard, then requires the static identity.manage mapping while those locks remain. The server must still supply freshly verified SDK issuer/subject/session/expiry and the exact hashed opaque credential; SQL arguments alone are not signature verification. Ordinary lookup needs no recent-auth assertion and preserves activity. Writes_enabled=false and a rotated epoch do not prohibit authorized historical review.

lookup_business_name_operation is a fixed security-definer routine owned by the existing restricted command owner. It clears caller business/actor GUCs before authorization, then sets transaction-local context only from that verified helper result. The owner receives only narrow SELECT columns on operations/audit, with forced-RLS policies requiring both selected business and verified actor. Web receives EXECUTE on this one reader and no table privilege, role membership or authority to set owner context. Forging GUCs cannot overcome that boundary. Every future owner routine must independently clear/derive context before reading; no generic context setter or caller SQL is exposed. Context is transaction-local and cannot authorize a subsequent request. Commit checkers remain independent of it.

Only command_type business.rename/schema1 is supported. Its typed receipt has exactly schemaVersion1, selected businessId, positive bigint businessVersion as a decimal string and auditEventId UUID. Validate the linked retained audit against the exact business/operation/actor, businesses entity, business ID/version and rename action before returning. Unknown/malformed stored command/receipt data fails review; it is not reported as confirmed absence. Other-actor/missing IDs return identical point-in-time absent evidence. Lookup is limited to the current actor's operations, not a general history/incident/financial search. Future broader incident access needs its own reviewed authorization.

The successful response contains only committed state, requested operation ID, the original operation recovery epoch and the strict receipt. It never reads/returns the current epoch, paused-write switch, name, raw request/result JSON, audit delta or credentials. The original epoch is historical evidence, never authority to auto-upgrade/resubmit an old command. Absence is not proof an in-flight command failed. Current authentication and permission checks precede every result, including replay review after recovery.

The server-only createBusinessOperationLookup snapshots its two UUID request fields before awaits, performs fresh SDK/local verification as background work, invokes only fixed parameterized SQL through the existing bounded restricted connection/TLS guard, and validates the exact response again. Its25-second overall bound and existing single-query statement/lock/deadline limits remain. Returned immutable evidence requires explicit forServer access and refuses automatic JSON serialization. All raw SDK/SQL errors and causes are suppressed, hashes are cleared, and no automatic retry, epoch replacement or activity update occurs. Export through the compiled Node application enables explicit trusted composition only; no HTTP route, executable authentication switch or UI business access is added.

There is still no production business.rename writer. CI-only definer writers and admin receipt seeds exercise real commit/lookup behavior; they are explicitly isolated fixtures, not authorized business commands. The receipt contract is now fixed for the first writer. That writer must enforce the recovery fence, expected version, typed canonical hash, current permission and source/audit/result atomicity before it can be enabled. This slice grants no production INSERT/UPDATE/DELETE on operations, audit or business data.
