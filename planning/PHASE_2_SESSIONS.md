# Phase 2: private session lifecycle and local prerequisites

2026-10-21. Owner continuation follows merged identity PR4 (main a5e784cbc9f64a7621d646452682e580bfe2e6d6; main checks run39541753170 passed). This slice implements session storage/lifecycle and local timeout prerequisites from SECURITY2 / DATABASE2 / F1. No canonical baseline is amended; no provider, purchase, real identity or deployment is provisioned.

## Recorded implementation choices

Schema ordinal3 adds private app_sessions and append-only session_events, owned by crest_schema_owner with enabled AND forced RLS, no policies, no positive runtime/provider table or helper EXECUTE grants. Existing restricted-role/default-grant contracts are checked before creation. The unchanged database-independent shell supports0..3; report/command versions remain0. Older schema1/2 regression suites stage their exact immutable SQL prefixes. Session tests migrate the previous two supported schemas1/2 and a fresh schema0; schema2's actual synthetic identities/history are hashed before/after upgrade. No historical posted-finance proof is invented.

The browser credential's SHA-256 hash is a unique32-byte field; the raw opaque cookie is never stored here. Provider session UUID is unique, linked to a durable owner actor without an auth-table cascade. New sessions require a live owner, matching session-security epoch and at least one active membership in an available business. This is structural validation of synthetic metadata, **not provider authentication**. Provider subject/issuer/MFA and session existence must still be verified before future session creation/access. No email-based or first-login owner rule exists.

Session lifetime and trust are fixed at creation: trusted maximum720 elapsed hours (30 days), untrusted12 hours. Expiry may shorten, never extend. Use elapsed hours rather than calendar days so DST/session timezone cannot add an hour. All timestamps are finite and cannot claim future activity, authentication or revocation. Cookie/provider bindings and issued epoch are immutable; a fresh login/security regeneration must create a fresh provider/app session, preserving old revocation history. Future verified reauthentication must also regenerate the browser session; this slice exposes no reauth command. Ordinary provider refresh changes encrypted token material only and cannot change initial authentication, trust or absolute lifetime.

Versions advance once per update. Activity/reauth timestamps cannot move backwards. Revocation is irreversible and atomically clears ciphertext/key metadata. Session-history changes are retained: no DELETE/TRUNCATE of session roots/history, no UPDATE of history. Token ciphertext is opaque bytes plus key ID; synthetic tests use explicitly fake placeholder bytes and do **not** prove encryption. Future encryption must use maintained authenticated-encryption/session libraries and provider SDK, not a custom cipher/format. No token generation, password/JWT verification or encryption implementation is introduced here.

Security history records creation, revocation, recent-auth assertions, expiry shortening and key-rotation metadata. Explicit before/after field allowlists exclude cookie hashes, provider session IDs, provider ciphertext, key IDs and any future secret column. Routine activity/refresh counters do not create one history row per poll. Payloads have schemaVersion1 and PostgreSQL17 jsonb SHA-256 digests; no external anchoring or administrator-proof claim. Attribution contains the database principal and claimed update actor; future commands must supply a verified actor. Provider refresh logs/attempts remain an adapter concern, without token/body logging.

## Local policy is deliberately insufficient for access

`localSessionEligibility` is a pure prerequisite evaluator, returning locally_eligible with providerAndTenantVerificationRequired=true, never authenticated/authorized. It validates server timestamps, live actor/security epoch, exact expiry, trusted168-hour foreground inactivity and15-minute recent authentication. At the exact boundary a session/assertion is expired. Untrusted sessions have the canonical12-hour cap; no additional unapproved idle rule is invented. Activity/polling/provider refresh cannot renew recent authentication. Expired/revoked/invalid requests never propose activity updates.

A successful foreground interaction yields only a proposed timestamp; apply it under a session-row lock **after every other request gate succeeds**. Background polling and provider refresh yield no inactivity extension. No cross-request authorization cache is allowed. Timestamps/snapshots must come from the server/database, never browser claims. The row-lock integration test proves serialization and rereading the first refresher's committed version; it does not exercise actual provider refresh-token rotation.

Before any positive business access: integrate maintained provider SDK/token verification and live provider-session lookup, password+TOTP enrollment/login/recovery, exact cookie flags and 256-bit opaque rotation, authenticated-encryption key handling, live membership/capability/tenant validation, CSRF/origin/no-store/safe logs/rate limits, transaction-local tenant context/pooling tests and the shared recovery-authority fence plus operation/business-audit framework for domain mutations. Local eligibility alone must never authorize a route. General web/worker credentials must not gain provider-table or service-role access.

## Evidence required

Unit tests cover trusted/untrusted exact millisecond limits, recent-auth boundaries, polling and refresh behavior, revocation/live epoch/disabled actor, malformed/future inputs and DST-independent elapsed time. `npm run test:sessions-db` uses real committed migrations through the pinned CLI/coordinator; it checks upgrades with retained identity history, closed actual grants/RLS, unique immutable bindings, creation prerequisites, database lifetime/DST/version rules, irreversible revoke/secret clearing, refresh-versus-reauth separation, safe retained history and actual refresh-row blocking. Missing infrastructure fails rather than skips. All prior suites and full build/browser/container/integrity gates must pass at the exact head before merge. Windows compiler limitation remains; these gates run on Linux CI.

The fake token bytes/identities are synthetic fixtures only. No SMTP, provider enrollment, hosted auth, live recovery, production migration privilege, independent backup or free production operating plan has been proven. Production activation and all existing gates remain blocked.

Provider references checked: [Supabase sessions](https://supabase.com/docs/guides/auth/sessions) documents JWT survival and session_id/live auth.sessions checks; [server-side advanced guide](https://supabase.com/docs/guides/auth/server-side/advanced-guide) describes customizable server storage. Provider-managed timeout settings do not replace Crest's application limits. These sources are design inputs, not deployed-provider test evidence.
