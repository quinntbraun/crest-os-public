## Packaging decision

Native Next Request lacks socket evidence. Use Next's documented programmatic custom server and route the reserved authentication namespace through createAuthenticationHttp before page dispatch. Other canonical targets use Next's getRequestHandler, with the actual HTTP server passed through its supported httpServer option. This is one application, not a separate API service. Next explicitly disallows combining a custom server with standalone output, so remove output:standalone and copy the normal .next build, public files, compiled server and lockfile-installed production dependencies into the existing pinned non-root Docker image. No framework internals, public header attestation, experimental loader or global React resolution override is used.

Pin MIT Rolldown1.2.14 directly as build-only tooling; this exact version was already locked through Vite. npm changes only the root declaration and peer-ownership metadata: no dependency version, registry archive or integrity changes. All269 locked packages retain reviewed licenses/integrity. Build local TypeScript server modules/configuration into ignored .local/server ESM; preserve runtime packages as normal external Node imports. Only the official server-only marker resolves its react-server empty export during this Node-only build. Next/React keep their default runtime resolution. Source modules still retain server-only guards for Next's client boundary. No key, database URL, owner identity or TLS material is embedded. The default production entry sets NODE_ENV=production before dynamically importing Next, so CREST_ENV=test cannot weaken document CSP. Development remains the existing Next development shell.

npm run build now builds Next and the Node entry; npm start runs the compiled entry. Docker installs production dependencies with disabled lifecycle scripts, starts server/main.mjs and keeps the existing read-only/non-root/capability-restricted smoke. The larger normal dependency/build footprint is a portability tradeoff; measured capacity and hosting budget gates remain before deployment. No paid tool/service is needed. Docker includes only the explicitly allowed build script in addition to previous source inputs.

## Request and delivery decisions

The adapter supports Node HTTP and an explicitly configured Node HTTPS listener. Production authentication requires TLS configuration and the existing resolver still verifies actual encrypted socket evidence; no forwarded-protocol fallback is added. Trusted server configuration supplies the existing provider/token-store/owner/database configuration; browser fields cannot select it. The default executable supplies no authentication configuration and has no environment activation switch: all reserved auth operations return fixed private503 JSON. It remains a setup shell. Optional TLS and production ingress still need genuine HTTPS/browser/deployment acceptance; constructor support does not prove a hosted platform's compatibility.

Require canonical origin-form targets, at most8192 characters, no authority/backslash/control/fragment/dot normalization and valid URI escapes. Reserve /api/auth and its descendants including encoded aliases before Next fallback. Actual raw header pairs feed Web Headers so duplicates cannot disappear through Node's parsed header map. Node limits headers to16KiB, and the adapter rejects more than128 pairs rather than silently truncating late security headers. Five-second header/keep-alive limits, ten-second body delivery limit,45second socket inactivity limit,128 live TCP connections and100 requests/socket bound transport resources. At most32 authentication handlers run concurrently; excess work returns private503 before flow IO. This capacity bound grants no authority or rate-limit refund and does not replace durable login/session work admission. WebSocket upgrades and malformed parser connections are closed. Exact resource numbers need capacity measurement before production.

Auth JSON bypasses the document Proxy, preserving the explicit deny-all JSON CSP, private/cache/CDN/surrogate no-store, security headers and cookie-only credential handoff. HTML/static requests retain Next's existing nonce/cache ownership and browser checks. No request header or exception is reflected. No Origin/CSRF/admission/SDK/local-session check is bypassed. Session evidence remains insufficient for business/tenant/recovery/capability authorization.

Abnormal incoming abort or outgoing close cancels the request; normal incoming body completion does not. Response body/write work is bounded by8192 bytes and five-second stages. A private WeakMap binds only newly issued login Responses to their own flow's cleanup. Settle once: successful Node finish forgets the callback; failed/aborted/oversized/stalled/write-error responses destroy the connection and run local-first cleanup under its independent four-second budget. A failed existing-session proof cannot revoke that device. Never parse Set-Cookie to recover a credential. The new disconnect scenario also exposed an earlier core-issuance gap: cancellation before returning IssuedSession revoked locally but left known provider material live. Core login failure now attempts local revocation first, then signs out only its captured fresh provider subject/session under an independent four-second deadline, including failure before local credential allocation. Five unit regressions cover cancellation, local/provider failures, pre-allocation failure and absent material; the actual disconnect regression remains required. Unknown/uncertain provider material and outages still require durable reconciliation. Cleanup failure logs only AUTHENTICATION_DELIVERY_CLEANUP_FAILED; startup/runtime failures also log fixed codes. SIGTERM/SIGINT stop the listener and close connections/Next, with a ten-second shutdown ceiling. Do not enable sensitive data before complete operational telemetry and orphan/retention/recovery procedures exist.

Node finish means bytes handed to the OS, not proven browser receipt. A lost response after finish remains uncertain, and atomic replacement may already have revoked the prior cookie. Database/provider outages can prevent cleanup; durable orphan reconciliation remains required. No transactional delivery guarantee, restored old session or refunded admission is claimed.
