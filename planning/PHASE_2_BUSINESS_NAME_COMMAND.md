Exact typed input has schemaVersion1, businessId, operationId, recoveryEpoch, positive int64 expectedVersion as decimal string and legalName. Every new accepted operation increments the aggregate version, including an explicitly submitted equal name; a retry uses its original operation ID and receipt.

Authorization requires fresh server SDK/local verification, current identity.manage and identity.read and the exact expected epoch/writes-enabled fence. A name is ordinary metadata: recent authentication is not required by SECURITY2 and this command never refreshes the recent assertion. The fixed definer clears caller business/actor/operation GUCs and sets transaction-local scope only after current authorization. Web has only fixed EXECUTE, no direct table/role power. New source/operation/audit/identity-history grants belong to the restricted nonlogin command owner under forced RLS; session activity remains a fixed session-owner helper. No INSERT/UPDATE permission is granted on recovery authority, membership, actor identity or financial tables.

Lock order is actor SHARE, business root UPDATE in the authorization phase, session UPDATE, recovery authority SHARE, operation claim, source/history/audit/result, then reentrant validity/activity checks. Acquiring the root exclusively before the existing generic fence avoids concurrent SHARE-to-UPDATE upgrades. This exclusive root is specific to changing that same tenant identity root; it is not a proposed mutex for future ordinary CRM/finance writes. The server calls the fixed typed routine directly in the existing bounded command transaction, never acquires the generic SHARE-root fence first, and performs no external network I/O while locks are held. Real two-device barrier tests must verify serialization and rollback.

The database hashes a fixed PG17 JSONB-text/UTF8-v1 structure containing command type/schema, verified business/actor, expected version as decimal string, recovery epoch and exact legalName payload. Caller hashes and server recorded timestamps are excluded. Unique business/operation claim precedes version validation. Matching retained hashes return the strictly audit-linked original schema1 receipt after fresh authorization and recovery checks, without comparing the original expected version against the advanced aggregate. Different hashes/actors/commands conflict without returning other-actor data. Version conflicts roll back the pending claim in a subtransaction and return only the authorized current version. No failed command leaves a pending tombstone.

Name/version/provenance, existing identity history, reconstructable safe before/after name+decimal-version audit, stable operation receipt and foreground activity commit atomically. Existing deferred integrity checkers run under their schema14 restricted role at genuine web COMMIT. Same-ID retries preserve source/audit/result and may advance session activity as a successful foreground interaction. Failure/conflict/lookup never advances it. Activity does not extend absolute expiry or authenticate. Historical identity_events retain their original schema1 representation; the new command audit/receipt uses decimal-string versions and existing portable audit hash input.

The private immutable server projection cannot auto-serialize. Confirmed receipt is returned only after actual COMMIT acknowledgement; fixed version/operation conflicts are distinct from outcome unknown.
