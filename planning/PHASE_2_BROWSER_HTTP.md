## Decisions and contract

The browser receives the existing opaque256-bit credential only through Set-Cookie. The adapters select explicit CSRF-token/absolute-expiry fields for JSON and never serialize provider identity, actor/session IDs, lifecycle evidence, password, access/refresh tokens or the private handoff object. Successful logout returns the confirmed local-revocation flag and actual best-effort provider outcome; provider failure is not presented as remote signout success. Generic failure has no exception/body argument, returns the same400 JSON error and does not clear an existing cookie. HTTP dispatch must catch private errors and use that response without logging raw errors, request bodies or headers.

Cookie names are exactly `__Host-crest_session` (SECURITY2) and `__Host-crest_login` (anonymous ten-minute proof context). Both use Secure, HttpOnly, SameSite=Lax, Path=/ and no Domain. No HTTP/development weakening of the cookie attributes is provided. The login-context cookie persists no longer than its database expiry and600seconds. Trusted login persists only until the original verified database deadline, at most2592000seconds; Max-Age is the remaining duration rounded down, never a new30-day window. Untrusted login uses a nonpersistent browser-session cookie with a server-enforced12-hour maximum. Browser session restore may preserve a session cookie, so closing the browser is not a revocation guarantee. The accepted login input's boolean must be passed unchanged to loginResponse; it affects cookie persistence, while verified server state remains the authority for access and expiry. Less than one remaining second, invalid timestamp or out-of-budget expiry denies response construction. Clock skew can deny issuance but cannot extend database validity; monitor clock health before deployment.

Login clears the pending cookie. Proof reissue emits no Set-Cookie and cannot slide a persistent deadline. Confirmed local logout clears both cookie names with matching attributes and Max-Age=0/expired Expires, even if provider signout fails. An uncertain local revocation must not use the success response. Cookie deletion cannot retract copied credentials or replace database revocation. Login/session response-construction or network failures after committed issuance/replacement require orchestration cleanup/recovery handling when routes are wired; the HTTP serializers alone do not promise transactional delivery.

The Cookie reader caps the UTF-8 header at8192bytes and128pairs. It validates pair grammar and exact canonical opaque values, never URL-decodes credentials, never chooses first/last duplicate reserved names and rejects comma-joined ambiguous headers. Unknown valid cookie names carry no authority. A malformed reserved cookie denies; the eventual UI must provide a safe expired-cookie clearing/retry path. No substring/name-prefix matching or identity claims come from cookies. Missing cookies are allowed only as parsed absence; callers still must require the correct credential for the selected flow.

The body reader requires POST, the existing exact configured Origin/JSON/fetch-site policy, and a single shallow JSON object. Login permits only email/password/six-digit code/boolean trusted and the same field bounds as the orchestration; bootstrap/session/logout permit only `{}`. JSON.parse and explicit boundary checks reject unknown/nested/missing/wrong-type fields; a count of separators outside valid JSON strings additionally rejects duplicate keys, including escaped equivalent names. This count is specific to the validated shallow schema, not a general JSON parser. Passwords are not normalized. Invalid UTF-8, BOM, trailing values, encoded bodies, reused/missing streams and invalid/mismatched Content-Length deny generically.

Every body is limited to8192 actual bytes and a five-second overall read deadline, regardless of declared Content-Length or chunking. UTF-8 decoding handles split multibyte sequences. Client abort and stream errors fail closed; read failures cancel without waiting on an untrusted cancellation promise. Empty chunks deny so an infinite microtask read loop cannot starve the timeout. This does not bound bytes already buffered upstream, initial header delivery or connection count. The future HTTP server/ingress must additionally enforce header/body/connection/time limits, authenticate proxy metadata and provide a trusted literal IP. Host, referer and forwarding headers never substitute for Origin.

Every response uses private/no-store/max-age=0, Pragma:no-cache, Expires:0, Vary:Cookie,Origin, nosniff, DENY framing, no-referrer and same-origin resource policy. No CORS allowance is added. JSON responses use a deny-all CSP; this is not the required nonce-based HTML script policy. HTML/SSR and failure/method responses also need complete no-store and nonce CSP integration before any authentication routes open. HSTS remains gated on verified HTTPS. These adapters are input/output mechanics, not authentication, endpoint admission, membership/capability or business authorization.
