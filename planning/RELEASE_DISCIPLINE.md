## One migration authority

Supabase CLI 2.121.0 is the sole apply/history authority; ordered SQL files live in supabase/migrations. Do not use dashboard schema changes, ORM push, auto-down migrations or a second application migration engine. Names are `YYYYMMDDHHMMSS_description.sql`; UTC versions must be unique and increasing. Committed migration-checksums.json records each version/filename/SHA-256 in order. Keep LF bytes; never edit/reorder/remove an applied migration, even if its checksum is recomputed. Add a corrective migration. `verify:migrations` checks files against the registry and, when VERIFY_BASE_REF is an exact PR-base SHA, enforces its immutable prefix. CI compares against the real PR base. The original preparation commit is the sole permitted missing-registry bootstrap.

Before the first Phase 2 schema migration, implement and test the controlled CLI apply coordinator: one session-capable pg connection holds a fixed advisory lock through verification, CLI execution and receipt verification. Every release operator uses it; no parallel direct CLI applies. Check the committed checksums against the prior successful release/DB receipts, then use the pinned CLI on the explicitly selected isolated target. Record applied byte hashes, resulting CLI schema_migrations history and release/source identity together in a reviewed receipt. If apply succeeds but receipt completion fails, fail closed and reconcile actual SQL history against the reviewed artifacts; never blindly rerun or auto-repair history. Test failures, checksum drift and concurrent runners on real PostgreSQL before any domain schema depends on it. The Phase 1 pgTAP harness uses a transaction advisory lock, but is not that production migration coordinator.

No executable production apply or reset command is provided in this slice. Do not run `db reset` against a hosted/linked/real database. Local CLI configuration disables API/Auth/signup, storage, seed loading and extra services; Phase 2 reviews these settings before identity testing. The compose database is a separate disposable harness, not a Supabase cloud project or the application database.

## Compatibility and review

Expand compatible schema first, deploy code accepting old/new, backfill resumably with verified controls, and contract only in a later reviewed release. A SQL change must update checksums, release compatibility and requirement-linked DB/grant/security tests. Before a schema release, migrate from the previous two supported release schemas with representative immutable/posted data and confirm hashes/totals/grants and compatible old-app behavior. There are no earlier application releases in Phase 1; do not invent two historical compatibility passes.

Use a 3-second lock timeout and bounded ordinary statements; measure expensive migrations against the defined large fixtures. Use direct/session-capable connections; transaction pooling cannot hold a migration advisory lock across CLI work. Roles/ownership/RLS remain enforced. No automatic destructive down migrations or history repair. Destructive changes need a recent tested restore and explicit release approval. If the old application cannot accept the resulting schema, stop writes and forward-fix or execute an incident-authorized restore/reconciliation; never silently downgrade the database.

## Candidate artifact and release record

CI builds a digest-pinned multi-stage Node Docker image, runs its non-root process with a read-only root filesystem, and tests liveness and the shell. It saves the tested image as a tar archive with SHA-256. `release:manifest` records source commit, dirty status, lockfile/registry/canonical/toolchain hashes, declared compatibility and optional Docker image ID. The local image ID is a content-addressed config identity, not a registry distribution digest; distributionDigest remains null until an explicitly approved future publication. Missing image ID or a dirty source tree means an incomplete candidate record, not a releasable artifact.

The short-lived GitHub artifact includes image bytes and metadata for review; it is not the independent recovery archive required by EXPORTS_AND_BACKUPS. Later production releases must preserve the exact tested image, source, migrations, config references, native/OS license materials, report/command versions and test evidence in the independent protected recovery package. Never include secrets in build context, image layers, reports or portable exports. `.dockerignore` permits only the explicit shell build inputs.

`Foundation checks` is the proposed CI check name, not yet an enforced branch-protection rule. Main protection remains unverified; no owner exception was granted. Do not merge around it. PR review/testing is permitted and no automatic merge/deployment/publication is configured. All D gates, applicable test tiers, real-device, accounting/security/export and restore requirements remain open. No production release is authorized by passing Phase 1.
