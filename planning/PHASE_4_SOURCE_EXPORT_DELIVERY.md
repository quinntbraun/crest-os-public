## Implemented capture boundary

Constructor configuration pins the business and database; no environment lookup, caller SQL, pool/sink callback, browser credential or runtime route. It uses the existing separate crest_export principal, never provider inventory/web privileges. A closed dedicated login with exactly one noninheriting, nonadmin export-role membership and no privileged role attributes is required. Production uses verified TLS. Test connections are restricted to loopback disposable migration databases. Configuration is copied and raw errors are redacted.

Own one connection and one READ ONLY REPEATABLE READ transaction. Obtain the configuration, identity and operation/audit contexts in one initial statement, giving all three the same statement timestamp and actual snapshot. Keep their intentionally distinct domain-separated scope fingerprints; they are not interchangeable tokens. Read every existing fixed source function through exclusive UUID pages of20 on that same connection. Never combine separate connections, snapshots, generations or later live queries.

Retain exact original UTF8 source JSON text, decimal-string versions, UTC microseconds and hashes. Check exact envelope/shape/scope/counts, forward cursor, body hashes, UTF8, per-source and aggregate bounds. Reuse the existing lossless configuration/identity/history verifiers and their latest-state/actor-reference join before committing. The aggregate limit is8MiB of evidence/10000records, with the component validators' stricter per-group limits; exceeding any limit fails the whole capture rather than truncating it. The30second overall deadline, bounded connection/query/lock/idle waits, connection-level errors and external cancellation tear down the owned connection. Concurrent calls to the same collector are rejected, with no automatic retry.

Only after COMMIT acknowledgment may the private wrapper return all three serialized source parts and matching generation/timestamp/counts. JSON serialization of that wrapper throws. Its trusted single-connection capture label does not change the offline verifiers' internal-consistency assurance, provide cryptographic provenance, authorize access, mark an export Ready, establish private custody, complete tenant/reference closure, or claim complete portability/backup. The collector does not deliver files.

## Encrypted private part custody

The next independent storage mechanism implements the existing EXPORTS_AND_BACKUPS2/ADR37/SECURITY8 encryption requirement using the already pinned JOSE library. Standard flattened JWE uses dir/A256GCM, fresh library-generated IVs, protected algorithm/key/purpose headers and authenticated immutable business/actor/export-job/generation/recovery-epoch/part/filename/media-type binding. The ordinary version1 JSON payload contains base64url original bytes, exact byte length and SHA256; plaintext content/checksums are encrypted, never exposed in JWE AAD or object metadata. This is a standard JOSE profile, not a new cryptographic algorithm. Export keys are explicit separate server configuration, copied into nonextractable CryptoKeys; no defaults, provider-token key reuse, key export, environment lookup or remote key URL. Retain prior keys for old parts during rotation. Decoded output is private, cannot serialize to JSON, returns copies only by explicit server handoff and supports disposal of owned plaintext buffers. Disposal does not promise erasure of every runtime/library copy.

createEncryptedExportPartStore prepares a private immutable intent before network effects: exact original and ciphertext byte lengths/hashes, key ID and stable exports/business/job/generation/part.jwe object key. Its owner must persist this complete intent under the future job/lease/recovery fence BEFORE attempting an upload. A prepared object belongs to one store instance and permits at most one PUT attempt; concurrent calls cannot send a second PUT. Conditional If-None-Match prevents replacement, objects are application/jose+json attachments with no-store, and the SDK retry configuration must resolve to exactly one attempt. No public/signed GET, list/delete, overwrite, browser credential, arbitrary object path or implicit retry is exposed. The production factory fixes the verified HTTPS R2 account endpoint and explicit credentials; no account or provider resource is provisioned.

After PUT acknowledgment, independently read all ciphertext under exact content-type/length/hash and stream bounds, then decrypt/authenticate the original binding and verify original length/hash before returning a custody receipt. Ignore ETag as a content proof. Reads are similarly bounded and verified. A lost/cancelled PUT may have committed: return the stable WRITE_UNCERTAIN error, retain the original prepared intent/key and prohibit another PUT. Explicit verifyCandidate reconciles that exact ciphertext, including across a new store instance with retained keys; a missing or failed read never authorizes replacement bytes. Failure/cancellation during the final GET returns no successful receipt. No storage call grants owner authority, proves source authenticity, marks a job Ready or enables a download.

Initial processing limits are8MiB original/16MiB JWE per part and60seconds across each I/O operation including configuration resolution and final verification. Fail bounds without truncation. Larger output must be explicitly split by the future formatter/worker rather than silently stored incompletely. No plaintext temporary file is written. Ciphertext candidates remain private for the future retention/reconciliation flow; this mechanism has no cleanup/deletion authority.
