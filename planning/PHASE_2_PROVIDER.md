## Recorded implementation choices

`src/security/provider-auth.ts` is guarded by `server-only`. Each operation creates and disposes its own official Supabase Auth SDK client with in-memory storage, persistence/automatic refresh/URL detection/debug disabled. Clients and credentials are never shared between login attempts. Configuration is server-owned: exact canonical `/auth/v1` issuer, HTTPS standard port and current publishable key only. Legacy JWT keys, secret/service-role keys, credentials in URLs, query/hash and arbitrary auth paths are rejected. Explicit test mode additionally allows HTTP on literal loopback only. Production configuration is not read from requests or browser inputs.

JOSE verifies ES256/RS256 signatures against the configured issuer's fixed JWKS endpoint. Exact issuer, authenticated audience/role, nonanonymous user, bound durable provider subject and session UUID, JWT type/key ID, integer issue/expiry timestamps, AAL and password/TOTP AMR are mandatory. The provider subject comes from the stored actor binding, never email equality or first-login ownership. JWT `jku`/`x5u` do not select network destinations and are rejected. Unknown algorithms, unsigned tokens, stale/future/malformed claims and missing MFA fail closed. Only public signing keys are cached (ten minutes; thirty-second unknown-key cooldown limits refetch pressure). Provider authorization observations are not cached across requests. Token issue time is never evidence of fresh password/TOTP authentication after refresh.

`authenticatePasswordTotp` uses SDK password sign-in then an enrolled, verified TOTP challenge/verification. It checks a fresh password AMR, online current user/factor, same provider subject/session throughout, final AAL2 password/TOTP AMR at or after the operation's start second, and a fresh live-session observation. Login inputs are snapshotted before awaiting IO. It returns server-only material with explicit `tokensForServerStorage()` handoff for future encryption and a JSON serialization guard. This is not a controller response. Tokens remain in memory; this slice stores none. A failed MFA ceremony can leave an unexposed AAL1 provider session until provider cleanup; disposal is local, not provider logout. No automatic retry/global signout is added. The future login lifecycle must test targeted cleanup without invalidating another device.

`verifyAccess` requires both expected subject and expected provider session from trusted app-session storage. Every call verifies the token, performs SDK online `getUser`, rejects unconfirmed/deleted/banned/anonymous users and missing verified TOTP, then invokes the required trusted live-session reader. It rechecks expiration/cancellation after IO. The result is only `provider_verified`, with `localSessionAndTenantVerificationRequired=true`. It cannot authorize a route or update local activity. Provider evidence must be combined with current app session, security epoch, tenant, membership/capabilities and recovery authority under the eventual transaction/command contract. No caller-controlled cached boolean may implement the reader.

The live-session reader is an explicit, required dependency, not an implemented production adapter. A subsequent migration must implement the canonical narrow, nonexposed `auth.sessions` lookup with minimal EXECUTE rights, exact subject/session ownership, and real PostgreSQL negative tests. Do not grant general web/worker access to provider auth tables or substitute `getUser` for session existence: a revoked provider session can leave an otherwise valid JWT. The current callback requires AbortSignal and must release its own resources on cancellation; the boundary rejects even if an adapter fails to settle.

Outbound calls permit only the fixed issuer's user/JWKS/password-token/factor challenge+verify endpoints. Redirects are rejected, bodies are capped at128KiB including chunked responses, requests time out at three seconds and the whole attempt at ten seconds. No provider Set-Cookie or incidental header is forwarded. All operation failures collapse to `PROVIDER_AUTHENTICATION_FAILED` without SDK causes or diagnostic bodies; no request bodies, passwords, OTPs, tokens, auth headers or identities are logged. Caller routes must still implement rate limits, CSRF/origin protection and safe response/log handling before exposing this boundary.

## Evidence and limits

`tests/unit/provider-auth.test.ts` exercises the actual pinned Auth SDK over a real ephemeral loopback HTTP server and JOSE with ephemeral ES256/RSA keys generated in RAM. Tests cover fresh password+TOTP, concurrent distinct subjects, input snapshots, signature/algorithm/header/claim rejection, current-user checks, same-session MFA, stale AMR, provider-session deletion while a JWT remains valid, no authorization caching, key cache/cooldown, redirects/oversized/chunked/malformed/outage failures, generic errors/serialization and real timeout/cancellation behavior. The only module mock is the `server-only` build marker for Vitest's Node loader. There are no mock crypto or SDK success returns. All fixture identities and credential strings are explicitly synthetic; no private keys are committed.

This fixture is not Supabase Auth, a TOTP verifier, or an auth database. Actual SDK requests and real JWT crypto do not prove provider enrollment, recovery, refresh rotation, live `auth.sessions` reading, account-loss recovery or hosted behavior. Those need the actual isolated Auth stack plus real database adapter tests before any positive access. No browser/session routes, cookies, encryption keys, enrollment/backup codes, login rate limiter, tenant context/RLS or deployed app exist in this slice. Existing real-data, recovery and free-production viability gates remain closed. Current authorized spend is$0.

Merge requires full existing lint/types/unit/integrity/dependency/secret gates and Linux CI database, production-build, browser/axe and container checks at the exact head. Windows loopback tests require approved sandbox networking; the host's compiler restriction still prevents local production build.
