# Phase 2: server-side session issuance and retrieval

2026-10-21. Owner continuation follows PR10/main c8bd14b9153c2b59be5344f82aee6f66e1f9f421, main CI39647607184 passed. Schema6 appends session creation/context/snapshot commands; original five migrations and canonical baseline stay immutable. This connects official Auth password/TOTP, standard JWE and opaque credential material through restricted runtime SQL. No HTTP route, new dependency, hosted account, paid service, real data or production activation is introduced.

## Decisions

The server lifecycle login API invokes the existing actual password/TOTP boundary itself; callers cannot submit a provider-evidence object instead. The durable subject binding comes from trusted server identity configuration, never email-based ownership or browser-selected actor IDs. After successful fresh MFA, session_actor_context reads only the exact stored issuer+subject owner with a live available membership. Unknown/unlinked provider users get no actor, membership or session. It never bootstraps an owner automatically.

The backend generates a fresh app UUID and256-bit credential, encrypts provider tokens with the existing JWE actor/session/epoch/issuer/subject binding, then calls issue_app_session. The database locks actor then associated business roots in UUID order, rechecks live epoch/disabled state/issuer/subject and active membership/available business, and checks the narrow live AAL2 provider reader. Supplied authentication instants must be finite, nonfuture and within the canonical15-minute recent-auth window; the server SDK enforces freshness from this specific login ceremony. SQL does not cryptographically verify the opaque JWE or AMR itself: the trusted application does, and later retrieval must decrypt and verify provider evidence before use. Compromised application credentials are not the canonical threat model's tenant-RLS guarantee. Forged SQL parameters cannot by themselves establish business authorization.

Creation, encrypted tokens/hash, original password/TOTP authentication instant, database timestamp/deadline and safe audit append commit together. Trusted expiry is exactly720 elapsed hours and untrusted exactly12, independent of DST. The backend never supplies created/expiry timestamps. Every login creates new material and permits independent devices. Retiring a previously presented browser cookie on login/privilege change/recovery remains part of the downstream complete browser lifecycle. No browser cookie is set by these modules.

app_session_snapshot accepts only the32-byte credential hash, returns a bounded server-only projection and never returns the hash itself. It denies revoked/disabled/epoch-invalid rows or missing encrypted tokens. The lifecycle validates local timestamps/expiry/idle policy, decrypts using the immutable row binding, performs fresh provider signature/issuer/audience/expiry/online-user/live-session checks, then rereads local state after provider I/O. A changed version/binding, expired JWT, revoke, disabled actor or changed epoch denies. No cross-request authorization cache. A concurrent change after this prerequisite phase still requires final transaction-held session/member/capability checks in the future request pipeline; session_verified explicitly carries tenantAndRequestVerificationRequired=true and never authorizes business data. Foreground activity is only a proposal; neither verification nor background polling writes activity or renews recent auth.

The new crest_session_owner is NOLOGIN/NOINHERIT/non-admin/non-bypass with no memberships, schema CREATE or provider-table privileges. It owns only fixed pg_catalog,pg_temp-path row_security=on functions. It has selected identity/membership/business/session column reads, app-session insertion and safe history insertion; no app-session update/delete/truncate. PostgreSQL requires an UPDATE grant for FOR SHARE: only immutable identity/business id columns receive that grant, with UPDATE USING true and WITH CHECK false so locks work while persisted identity writes are denied. All affected tables remain forced-RLS; web receives only function EXECUTE, with no direct table policies/grants. New function owner authority is distinct from the existing revocation owner. Existing provider helper additionally permits this closed owner to obtain its boolean, never auth-table data. Migration preflight rejects role/membership/CREATE/table-boundary drift.

Runtime SQL uses fresh bounded crest_web connections and rejects migration/admin/broadened logins. Production TLS verifies certificates and URL query overrides are forbidden; tests accept only explicitly owned loopback crest_migrate targets. Connection/statement/lock/query/connection-operation limits are1s/1.5s/750ms/2s/3s. A lifecycle call has a20s cancellation signal; the provider boundary now accepts/propagates caller cancellation while retaining its10s per-operation cap. Generic errors never include driver/SDK causes, tokens, credentials or query parameter values. Returned issuance material blocks JSON serialization and exposes only an explicit cookie-response handoff; verification returns metadata and outstanding-gate flags, never access/refresh tokens.

Failed or uncertain creation never releases the new credential. Best-effort local revocation uses a separate bounded connection even after caller cancellation (up to3s additional cleanup). Database outage can leave an unexposed uncertain app session; failed post-MFA issuance can also leave a provider session. No known credential is returned and retry must use a new login/material, not assume the old attempt failed to commit. Scoped provider cleanup/complete logout and orphan operational handling remain downstream. Token expiry currently denies rather than refreshes: locked provider refresh must be implemented before offering remembered browser sessions. No complete30-day browser-session reliability claim is made from a stored maximum alone.
