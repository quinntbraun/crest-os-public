## Runtime and browser decisions

createAuthenticationRuntime composes the existing restricted live-provider lookup, official SDK boundary and encrypted token store from explicit trusted server configuration. Require matching database/provider environments, the pinned owner subject/factor, a separate32byte login fingerprint key and explicit token encryption keys/active ID. It reads no environment variables and provisions no account. Its private object rejects JSON serialization and hands configuration only to the server deliberately. Copy mutable configuration on entry; existing constructors enforce database/provider/key constraints, while the dispatcher validates origin/ingress. The compiled application exports this factory under normal Node package resolution; react-server remains a build-time server-only marker resolution, never a global Next/React runtime condition.

The default executable still supplies no authentication configuration and has no activation switch. /sign-in renders the interface and reports setup unavailable from the fixed private503 response. The root setup shell links to it. No positive customer/financial/business route is introduced. A verified session is point-in-time device evidence; tenant membership, capabilities, transactional recovery/operation/audit checks remain mandatory for future business access.

The client uses only same-origin POST JSON bootstrap/login/session/logout, credentials:same-origin, no-store, redirect:error, no-referrer and a40second deadline around the existing35second server work ceiling. It accepts only bounded8KiB JSON and exact proof/logout shapes, validates canonical opaque CSRF syntax/expiry, never returns raw exception details, and never retries a mutation automatically. Only CSRF proof/expiry are held in component memory. HttpOnly cookies, provider credentials/SDK, owner IDs, database configuration and encryption material are absent from browser storage and client configuration. No local/session storage, third-party auth script, trace, analytics, automatic refresh loop or service worker is added.

Each explicit sign-in gets a fresh single-use pending context, then submits exactly email/password/six-digit TOTP/trusted. Native labels, username/current-password/one-time-code autocomplete, numeric code entry, visible focus, status announcements and44px controls support desktop and360px use. Trust starts unchecked and describes the existing30day absolute/seven-day inactivity limits. An untrusted cookie remains nonpersistent with the existing12hour server ceiling; no browser-close guarantee is claimed. Password/code DOM values clear immediately after submit; busy rendering removes the form. No password normalization, signup or recovery claim is added.

A successful login response is followed by a separate fresh session request before the UI claims success, proving browser cookie acceptance. Session checks on load, on focus/visibility/page restoration for verified or uncertain sessions, and an explicit Check session control obtain fresh proof without extending authentication/activity/deadlines or rewriting persistent cookies. A form awaiting credentials survives password-manager/window focus changes. Work is single-flight. Unmount aborts local waiting; mounted/operation guards discard stale completions. Cancellation does not prove a server mutation was undone. Login/bootstrap/logouts are never automatically replayed after uncertain delivery. An uncertain result hides signed-in controls and requires a fresh explicit/session lifecycle check; a confirmed local revocation can report local sign-out even if provider cleanup is pending. Signing out one device never means signing out all devices. No business records or protected dashboard are displayed.
