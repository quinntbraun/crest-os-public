## Problem and bounded change

Local revocation is authoritative and deliberately erases encrypted provider tokens/key IDs. Provider sign-out follows local commit and remains bounded best effort. If the process/provider/network fails, its in-memory provider reference can be lost. Retaining tokens after revocation would weaken the existing contract. Schema17 instead appends a private token-free reference to the exact revoked app session, actor, provider session, issued security epoch, source version, revocation timestamp and immutable source event/hash/operation. It records no cookie/hash, provider token, ciphertext, key, CSRF, password, contact or reusable authority.

The retained table is global security metadata like app_sessions, not a tenant business command or financial queue. Rows are permanently classified review_required: this means the local transition has evidence for later reconciliation, not proof of a provider failure, live session or successful provider sign-out. A normal successful SDK sign-out also leaves this reference. A later separately authorized consumer must verify actual provider state and append its own distinct evidence. No browser/status API, worker execution grant, provider admin credential, direct Auth-table mutation, token escrow, financial action or production switch is added.

## Integrity and permissions

The existing session_history trigger runs before the new zz_session_cleanup_reference AFTER UPDATE trigger. Only a first NULL-to-non-NULL revoked_at transition captures. A fixed crest_session_owner definer with pinned search_path/row_security reads the existing safe event projection and inserts the reference in the same transaction. Its BEFORE INSERT relational guard matches immutable source session/provider/actor/epoch/revocation/version and exact first-revocation audit contents/hash. Missing/ambiguous/corrupt evidence or insertion failure rolls back local revocation and its history; no partial local-revoked success may be reported. Existing local revocation already depends on transactional audit availability. No network call or new actor/business/recovery lock is added to this path.

The table is owned by crest_schema_owner with forced RLS. Only the nonlogin/noninheriting session definer gets INSERT; it receives a column-limited read of the already secret-free session_events. No raw web/worker/recovery/anonymous/authenticated access or direct trigger execution. No new role membership, general routine, CREATE privilege, source mutation power or provider grants survive migration. Reference updates/deletes/truncates are rejected, including migration-authority ordinary DML. Source tokens are still cleared in the original revocation transaction, with old16 SQL bytes unchanged. The reference never authorizes a provider action or bypasses signature/current environment binding checks.

Migration backfills only existing proven first-revocation SECURITY_CHANGED events, preserving all source rows/history and CLI receipts. It cannot infer undocumented revocation: sessions originally inserted revoked, unregistered AAL1/failed-login provider sessions, expiry/security-epoch invalidation without local revocation, unknown provider-side outcomes and lost pre-provider references require the later inventory/reconciliation design. No completeness claim is made for those cases. No automated cleanup/retention purge is added. References/source history remain in recoverable DB state; later authorized security exports must include this open relational metadata without credentials. The ordinary customer export does not gain global security metadata access.
