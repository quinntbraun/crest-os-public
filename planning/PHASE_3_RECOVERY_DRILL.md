# Synthetic database recovery drill

2026-10-24. First bounded native recovery proof under ROADMAP Phase3, EXPORTS_AND_BACKUPS5/7 and SECURITY7. Baseline PR58/main98461af19ecb0c871e425b97bcc801a83c0e5026. No canonical amendment, database migration or production authority change.

## Delivered scope

`tests/support/recovery-drill.mjs` uses real PostgreSQL17 `pg_dump` custom archives and official age1.3.2, with checksum-pinned Linux/Windows downloads and executable version checks. These are synthetic-only development tools: explicit test environment, loopback/random disposable database names, owned fresh Docker cluster, no production override. The source uses the existing migration coordinator and actual digest-pinned provider DDL plus all31 application migrations. The independent destination starts from template0 in a separate digest-pinned PostgreSQL cluster; application migrations are not reapplied to substitute for restoration.

Hold one exported READ ONLY REPEATABLE READ snapshot for original row fingerprints and schema capture, then dump against that snapshot while an actual typed business command commits on another connection. Encrypt the dump and manifest with a public age recipient only. Keep ciphertext lengths/hashes in a private receipt. An emergency-kit key copy restores in a fresh Node process without the source URL/credential or original key file. Fully decrypt/authenticate and verify the plaintext hash before executing any archive SQL. Reject a destination with existing tables, sequences, views, types, functions or nondefault schemas; use pg_restore `--exit-on-error --single-transaction`, retaining owners, grants, constraints, triggers and RLS. Compare original row text and schema bytes after restore, normalizing only PostgreSQL's random psql restriction nonce.

Recreate only the current closed nonlogin Crest role definitions, checking deny-by-default flags and absence of internal role memberships. Runtime login credentials/memberships are deliberately excluded and must be separately reprovisioned. Provider built-in roles/extensions come from the independently started pinned image; actual provider users/schema/migration data are in the encrypted database dump. This is not neutral-provider/account-loss compatibility proof.

The fifteen native cases cover separate-cluster/fresh-process recovery, concurrent snapshot consistency, original operations and exact bigint/microsecond/binary/Unicode/sequence preservation (including a previously unknown fixture schema), private encrypted artifacts/emergency-key recovery, wrong key/missing/truncated/tampered ciphertext, refusal to overwrite existing rows or function-only state, restored RLS/role/grant/FK/check/append-only enforcement, unchanged source, and restored authority/session fencing. A drill-only administrative fixture records a fresh incident/epoch outside the restored DB, pauses writes, revokes local/provider sessions and rotates actor security epochs. Old credentials are denied; fresh credentials cannot replay known or absent old-epoch commands, or bypass paused writes. Only an explicit synthetic reviewed new-epoch action enables the final test mutation; original operation history stays retained.

## Limits and remaining work

This is a database development drill, not the production backup service, complete recovery kit or incident command. No runtime grant/role/function is added. The manifest explicitly says `completeBackup:false` and lists exclusions: external objects, independent vault, app/image, production configuration and production recovery authority. Existing source remains running independently during the drill; actual old-runtime/worker/credential drain/fencing is NOT proven by testing rejection on the restored database. Production recovery requires separate incident-specific authorization and implementation of that boundary, as the canonical runbook requires.

Bound the fixture to32MiB child output/dump and8MiB total row text,10000 rows/table; fail on overflow. Plaintext stays in bounded process memory, never a disk dump or CI artifact. Keys/private files use0700 directories/0600 files in ignored `.local/recovery-drill/`; runner destruction removes private synthetic material. This is not streaming/capacity/RPO/RTO proof, and sequence/global-role DDL concurrency is not claimed snapshot-safe. No files/vault/retention/heartbeat, configured owner identity recovery, independent image/key/config recovery, full source export, neutral import or production reopen is claimed. Their finite Phase3/release work remains mandatory.

Install recovery tools and run `npm run test:recovery-db` in the isolated foundation CI group, serial with its existing role-owning suites. All pre-existing jobs/checks remain. Local Windows can execute the native age checks; actual PostgreSQL/Docker/Auth/build/browser verification comes from exact-source Linux candidate and protected actual-main CI. Record actual results/bindings in the PR; planned747 DB/Auth (including109 genuine Auth),1915 unit/45 files,9 pgTAP,16 shell and18 HTTPS leaves are not passes until executed.

Sources: [PostgreSQL17 pg_dump](https://www.postgresql.org/docs/17/app-pgdump.html), [pg_restore](https://www.postgresql.org/docs/17/app-pgrestore.html), [official age1.3.2 release](https://github.com/FiloSottile/age/releases/tag/v1.3.2). PostgreSQL archives contain executable SQL and must come from a trusted recovery point; encryption/checksums alone do not authenticate who created one. No real data, provider/vault account, spending, deployment or production activation.
