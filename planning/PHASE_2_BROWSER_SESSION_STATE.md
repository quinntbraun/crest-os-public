## Decisions and ordering

The selected initial login is one password+TOTP submission. Trusted server configuration supplies the explicitly provisioned subject and verified factor ID; the request can supply only email, password, six-digit code and a boolean trusted-device choice. Unknown fields (including subject/factor/actor selection) deny. The SDK performs actual fresh password/TOTP verification and durable subject binding. Pending-login state is an anonymous CSRF context, not an AAL1/provider session: no password, TOTP code or provider access/refresh token is stored there. This avoids persisting credentials between MFA steps and preserves the current controlled single-owner identity model. A future multi-user resolver must retain immutable subject/membership checks rather than authorize by email.

Anonymous bootstrap first requires exact configured Origin, allowed mutation method/JSON content type and permitted fetch-site context. It generates an independent256-bit opaque credential and random CSRF token with a login-purpose/UUID binding. Only the credential hash, keyed trusted-IP fingerprint, CSRF hash and database timestamps enter SQL. The durable context expires exactly10 elapsed minutes after creation, is IP-bound and can be consumed only once; consumption clears its CSRF hash. The prior presented pending context is consumed when a replacement bootstrap succeeds. Malformed old cookies are discarded during fresh bootstrap, while valid current credentials are always strictly validated. Bootstrap establishes no user identity or business authority.

Bootstrap shares schema8's stable-key singleton lock and binds/checks the same HMAC-key fingerprint atomically. Separate context budgets are20 per IP and1000 total within a rolling15 minutes. They protect finite anonymous state without consuming the canonical login-attempt budget. All created contexts count even when consumed or expired at10 minutes. Cleanup removes at most256 contexts older than15 minutes per request. These are documented initial operational bounds, not a measured public-scale/DDoS guarantee or a permanent account lock. Clock/backlog/ingress trust and scheduled physical cleanup remain operational production gates. A different/missing server key cannot create an independent counter namespace.

Login reads the matching unconsumed/unexpired IP-bound context, verifies the login-purpose synchronizer proof and Origin, and atomically consumes it before admission/provider work. Then it durably reserves the canonical5/identifier and20/IP login attempt before invoking the existing fresh password/TOTP issuance. Failure/outage/uncertain consumption requires a new context; there is no replay of the same pending proof or stored password. Concurrent submissions have one consume winner and at most one actual new provider/app session. No database lock is held across password/TOTP network I/O.

After actual issuance, bind_browser_session locks all affected actor roots and then session roots in UUID order. It rechecks local revoke/epoch/disabled/absolute expiry/trusted idle and the live AAL2 provider session, inserts the session-bound synchronizer hash, and retires the previously presented local app cookie through the existing irreversible revocation command in the same transaction. Malformed/unknown prior cookies cannot select an actor or prevent recovery by a fresh verified login. Failed binding leaves no partial CSRF/old-cookie replacement; failed or uncertain completion releases no new credential and attempts separate local/provider cleanup with a fresh4-second deadline. The flow re-verifies provider/local state before returning its private handoff object. The overall flow signal is30s; nested lifecycle/provider/database bounds remain in force.

Session synchronizer proofs are a separate forced-RLS table with at most8 hashes per app session. The just-issued proof is always retained even when timestamps tie or step backward; up to7 prior proofs support multiple tabs. A ninth issue retires the oldest retained proof; a stale tab must bootstrap a fresh proof before mutation. Reissuing a proof requires exact Origin and fresh provider/local verification, then a database-fenced bind and final verification. It never renews authentication, foreground activity, expiry, trust, security epoch or session row version. Login and authenticated-session CSRF purposes cannot substitute for one another. Only hashes are stored; raw tokens are explicit response handoffs and accidental JSON serialization throws.

Bootstrap and CSRF reissue establish request-proof state; they do not authorize a business mutation. Before exposing them through HTTP, route-specific body limits, no-store responses, cookie rules, nonce CSP, trusted ingress/IP policy and durable session endpoint limits must be wired and tested. Every actual protected mutation still requires the current session-bound synchronizer proof, exact Origin and downstream tenant/request authorization. Session evidence continues to carry tenantAndRequestVerificationRequired=true. No direct core-lifecycle call may replace this orchestration in future browser routes.

Logout requires exact Origin and a retained matching session-purpose proof. Retained proof lookup deliberately grants no positive session eligibility, allowing local logout of expired/epoch-invalid/already-revoked sessions. The lifecycle attempts to capture encrypted provider material, commits local revocation first, then decrypts and requests only that provider session's local signout using the official SDK and public publishable-key configuration. The SDK admin.signOut method uses the supplied access JWT at the normal /logout?scope=local endpoint; no provider administrator secret or implicit token refresh is introduced. A provider failure returns localRevoked=true/providerSignedOut=false after known local commit and cannot restore access. Repeated local logout adds no version/audit event. Invalid/missing CSRF or unknown cookies fail generically before revocation.

If epoch/disable/revocation or a database read failure prevents capture, or the provider rejects an expired JWT/signing key, provider signout is best effort and must not be claimed complete. Replacement retires the old local cookie atomically but does not claim the old remote provider session was signed out after its ciphertext was cleared. Failed issuance and replacement can therefore leave remote sessions whose credentials are no longer exposed by the application. Provider-session/orphan operational cleanup and deployed recovery/revocation drills remain required before production. Previously captured independent provider credentials are not erased by deleting local ciphertext. In-flight work and already-streamed bytes retain the canonical revocation limits.

## Database privileges and evidence

No new role is needed. Closed crest_login_owner gains only the private context reads/inserts, consumption-column update and expired-only delete required by its fixed-path functions. It gains no actor/session/provider access. Closed crest_session_owner gains the bounded private CSRF table and EXECUTE on the existing narrow revocation function for atomic replacement; its existing actor/session lock privileges remain unchanged. Web receives EXECUTE only. New tables stay owned by crest_schema_owner with forced RLS. All functions use pg_catalog,pg_temp and row_security=on, reject malformed inputs and require READ COMMITTED. No generic session update, direct runtime table grant or membership privilege is added. Context/CSRF tables are operational proof state, not business/financial history; scheduled pruning of obsolete session proofs and backup retention remain downstream.
