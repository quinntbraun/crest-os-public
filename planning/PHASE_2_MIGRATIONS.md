## Scope and contract

Implement the prerequisite in RELEASE_DISCIPLINE before any identity/domain schema migration. Supabase CLI2.121.0 remains the sole SQL apply/history authority. The coordinator reads/checks ordered migration bytes, holds one session-level PostgreSQL advisory lock `(8291,2)` throughout verification, CLI execution and receipt verification, stages a separate fixed snapshot, invokes only `db push --db-url ... --skip-vault --yes --agent no`, and verifies the actual CLI history. No roles/seed/vault application, project linking, history repair or destructive down command is introduced.

This slice deliberately supports **disposable local/CI targets only**: CREST_ENV=test, literal loopback IP, required credentials, no caller URL options, and a database named crest_migrate_ plus16 lowercase hex digits. The existing crest_test database, hosted targets, localhost name resolution, staging and production are rejected. No escape flag exists. The integration harness creates each uniquely named database from template0 and removes only a name it successfully created and recorded itself. The normal CLI entry additionally requires a clean Git checkout and obtains the exact source commit automatically.

The application migration registry remains empty. All SQL in integration tests is generated synthetic harness material, not application migrations. ## Receipt and failure behavior

The approved receipt ledger is separate from SQL history: `.local/migration-ledger/<database-incarnation-hash>/`. Fingerprint the actual PostgreSQL system identifier, database name and OID; recreating a database is not adoption of an old release. All operators targeting that database **must use the same protected ledger**. Test fixtures supply one shared root to competing coordinators. Local receipt storage is implementation evidence, not the independent protected production recovery store required by the architecture.

Require an explicit empty bootstrap with no application relations or existing migration history. Thereafter require the checksum-verified finalized HEAD receipt. Applied files must be an unchanged prefix, and database history (version/name/statement hashes) must exactly match the previous receipt. Unknown rows, missing/corrupt receipts, changed history and applied-byte rewrites block apply. No-op runs verify history without reapplying SQL and retain release/source lineage.

Before CLI execution, exclusively create/fsync a pending marker. It survives CLI failure, partial multi-file success, process death, guard loss, source drift and receipt-store failure. A subsequent run stops for review instead of guessing whether to replay. Final receipts contain original byte hashes, source commit, pinned CLI version, observed target, complete resulting CLI version/name/statement hashes and previous receipt digest. Write once, fsync/read back, atomically publish HEAD, verify the guard again and only then remove pending. No connection URL/password or SQL text is written into receipts or public logs. CLI password is passed in PGPASSWORD, not argv. Child environment excludes ambient provider tokens, PG target/service settings and project overrides; private CLI home and disabled telemetry stay within the ignored snapshot directory.

CLI startup parameters set lock_timeout=3s and ordinary statement_timeout=30s; CLI has a120s process bound. Guard connection loss aborts the child and retains pending; do not release a live guard until the child has actually closed. Previous successful CLI rows remain unchanged. Failures never trigger auto-down, auto-repair, automatic pending deletion or an inferred successful release.

An operator must preserve the pending/snapshot files and inspect actual CLI history and artifacts before any separately reviewed reconciliation. This slice intentionally provides no automated reconciliation command. A local malicious administrator can rewrite files and database history; these receipts are not administrator-proof audit evidence.
