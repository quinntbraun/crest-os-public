## Recorded storage profile

Use the existing exact JOSE6.2.13 dependency and standard RFC7516 Flattened JWE JSON Serialization: direct symmetric key management alg=dir, authenticated AES256-GCM enc=A256GCM, protected kid and typ=application/vnd.crest.provider-tokens.v1+json. JOSE generates every IV; callers cannot supply nonces. No custom cipher, password derivation, compression, remote key lookup, unprotected headers or alternate algorithms. The application profile permits exactly protected/aad/iv/ciphertext/tag envelope fields and alg/enc/kid/typ protected fields. JSON uses JSON.stringify UTF8 serialization; duplicate names, alternative whitespace/escapes, malformed UTF8 and noncanonical base64url fail closed. This is a strict application profile of standard JWE, not a general JOSE parser.

External authenticated data is UTF8 JSON.stringify of the ordered array ["crest.provider-tokens.v1",actorId,appSessionId,providerSessionId,securityEpoch,subject,issuer]. UUIDs use lowercase canonical spelling. Issuer must be the exact canonical /auth/v1 HTTPS URL with default port, or test loopback HTTP. These immutable identifiers are already database metadata; AAD is authenticated but visible, never a place for secrets. Decrypt compares the expected trusted row/actor context before JOSE verifies authentication. Moving a ciphertext to a different actor, app/provider session, epoch, provider subject or issuer denies. The caller must obtain this context from trusted live server state, never browser claims.

Plaintext is exactly {accessToken,refreshToken}. Provider token characters are limited to ASCII letters/digits and dash/dot/underscore/tilde; access is at most16384 characters, refresh32768. The complete UTF8 JWE must fit the existing65536-byte database constraint; combined token sizes can therefore fail even within individual limits. No truncation or plaintext fallback. Decrypted material holds tokens in private fields, blocks JSON serialization and requires an explicit server-only tokensForProvider handoff. Generic fixed errors omit SDK/JOSE causes, inputs, keys and plaintext. This cannot prevent a trusted caller from deliberately logging handed-off strings, nor guarantee erasure of JavaScript/WebCrypto memory.

The factory requires an explicit active key ID and1..16 unique named32-byte keys from trusted server configuration. IDs use1..100 ASCII letters/digits/dash/underscore. There are no defaults or environment/configuration provisioning in this slice. Input keys are copied synchronously before asynchronous work, imported as nonextractable WebCrypto AES-GCM keys, and temporary raw copies cleared after import. The returned store exposes only encrypt/decrypt. Real keys must be random from a cryptographic generator, stored separately from source and database backups, with restricted server access. Fixture keys exist only in RAM; no production key is generated here.

Rotation uses a new active key while retaining named old keys for decryption; re-encryption produces a fresh JWE under the active key without changing binding or local authentication/deadline fields. Unknown, removed, wrong or mismatched key IDs deny. Operational replacement must run under the existing session row lock/version discipline; the pure crypto component never writes a database. Future commands must serialize provider refresh and token replacement and recheck revocation/epoch/membership at commit. Removal of an old key requires completed replacement or session invalidation. Encryption is not replay protection: a stale authenticated ciphertext remains decryptable while its key is retained. Every request still requires current local revocation/epoch, provider verification and tenant capability checks. Key loss requires safe session invalidation/re-login, never plaintext recovery. Key custody/restore and deployment rotation procedures remain unproven production prerequisites.

## Evidence and limits

Thirty-eight unit cases cover independent JOSE interoperability in both directions, randomized encryption, all six binding fields, tampered JWE components, wrong/retired/rotated keys, mutable configuration, envelope/header restrictions, malformed/duplicate/oversized records, authenticated invalid plaintext and secret serialization. A forgery test changes both the embedded AAD and expected binding, or both key labels with an identical underlying key: matching metadata must still fail GCM authentication. Actual Auth/PostgreSQL integration adds a fifteenth scenario: real password/TOTP provider tokens encrypt, persist as bytea, load, decrypt and verify through the existing live reader; rotation preserves local timestamps; row substitution denies; audit projections omit secrets/storage metadata; revocation clears ciphertext/key while a retained stale ciphertext still cannot establish local eligibility. Test database administrator writes are fixture-only and grant no runtime table access. There is no new database adapter or authorization claim.

Full CI must pass at the exact reviewed head, including existing database/real Auth suites, provenance/dependency/audit/secrets, lint/types/unit, production build, browser accessibility and restricted container smoke. Windows cannot run Docker or the approved production compiler locally, so those checks require Linux CI. Review is by the implementing assistant, not independent security certification.

Browser login/pending-login storage, opaque cookie handling, durable abuse/CSRF controls, runtime session commands, provider refresh locking, live tenant/capability context and recovery remain downstream. Successful crypto does not unlock business data, production use, accounting, paid services or deployment. Current spend remains$0.
