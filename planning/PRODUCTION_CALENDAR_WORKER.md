# Production Calendar dispatch foundation

This implementation adopts the existing Calendar event projection, durable lease/send-admission/reconciliation logic under a production worker composition, plus the real initial browser authorization/setup flow described below. It is not complete Calendar integration or launch acceptance. The actual release remains blocked; refresh, safe abandoned-authorization recovery and disconnect/revocation remain required.

## Initial browser authorization and consent

The web profile now pairs `googleCalendar` with a required private `calendar` block: `connectionString`, `clientId`, `clientSecret`, `verifierKeyId`, `credentialKeyId`, `calendarKeyMaterial` (canonical base64url 32 bytes), and `googleOwner` (the account the owner reviews before connecting). The setup login must differ from the ordinary web login on the same database. PKCE and credential key IDs differ, and integration key material cannot reuse authentication login/token keys. Browser callback origin/path are derived solely from the canonical application origin. Unknown fields and insecure endpoints are refused.

The dedicated `crest_calendar_oauth` executor retains its fixed command allowlist, verified database TLS and closed-role/membership checks. Production settings availability/mode are derived by the actual server composition. The initial setup page obtains account information only after fresh session and database business/recovery/`identity.manage` authority checks; failed authority returns no configured account email. The owner explicitly reviews that account and approves calendar creation before the POST start route records the existing attempt/creation intent. The authorization URL uses the existing PKCE/state binding and fixed narrow Google scope, with an account hint; the client separately rejects foreign URLs/callbacks, duplicate parameters, broad scopes and missing PKCE before navigation.

The actual callback namespace is reserved by the Node adapter, including encoded aliases. Callback processing requires the actual Crest cookie/session, fresh authentication and current business recovery epoch; the existing connection verifies one-use actor/session/business/epoch-bound state, PKCE and committed exchange authority before provider IO. Every success/failure returns the existing clean settings redirect without reflecting a code, state or exception. Unconfigured and test-workspace callbacks are also cleaned and cannot fall through to Next or the synthetic provider. Ordinary POST routes retain Origin/CSRF/admission checks; the narrowly scoped state-bound callback does not require Google's navigation to forge an Origin/CSRF header.

After initial creation, the existing saved-destination disclosure, sharing and notification review remains separate and required before consent becomes active. Live labels/activity use real saved statuses; fixture preparation/copy remains confined to test mode. Private account/context data clears on hide, sign-out, recovery pause or failed access. No browser key/token persistence, automatic event-sharing opt-in, manufactured callback/grant or simulated provider adoption is added.

## Implemented boundary

The production worker requires a business-scoped `googleCalendar` capability with the existing scheduling dependencies. Its query adapter uses the existing closed `crest_calendar_dispatch` role, explicit restricted-login membership checks, verified database TLS, fresh transactions and an exact SQL/parameter allowlist. `next_fictional_google_calendar_job` is a retained historical name: its body checks the registered worker principal/business, recovery authority, consent generation and retained work. No SQL, schema, principal mapping, grant or consent was created or changed here.

The worker uses only fixed Google provider transports. Its actual destination is the valid secondary-calendar ID in the committed dispatch lease, not the fixture's fixed calendar ID or a browser field. Projection still requires explicit disclosure flags, private visibility, no reminders/guests, exact appointment identity and a retained mapping marker. Provider reads/writes retain durable admissions, exact send bodies, ETags and uncertain-write reconciliation. No transport reply alone creates an application success state.

Synthetic construction retains its original loopback/provider identity guards and fictional destination. The shared dispatch core does not allow a production request adapter through those fixture guards. Conversely, production construction refuses missing/foreign-business composition authority before provider/database work.

The production entry is a bounded single tick suitable for the already planned scheduled worker, using the same release image. It opens no listener and holds no ordinary web/session credentials. It logs only a fixed validated outcome name; a published/removed state is available only through existing confirmed provider and committed database evidence. Delayed, reconnect, review, uncertain and idle outcomes remain distinct.

## Decision: restart an initial authorization before any provider request

Migration 127 changes the creation-intent primary key from business alone to `(business_id,attempt_id)` while preserving every existing intent and its existing composite references. Multiple historical attempts are necessary to recover from an abandoned Google navigation; only one unretired intent is allowed by the serialized, restricted command flow. Confirm refuses a new intent until the previous one is explicitly abandoned. The business advisory lock is shared with authorization start/consume/exchange and first-destination creation. Ordinary runtime roles receive no direct table writes.

The new append-only `google_calendar_creation_abandonments` table links the original intent to the current fresh owner's actor/session/recovery authority and a committed, auditable operation. An explicit confirmed command requires `identity.manage`, current recovery/write authority, no saved destination, and no admitted code exchange, Calendar creation admission or retained creation result. It retires the old ephemeral authorization link and records abandonment without editing or deleting the intent. Repeating the same operation returns its committed result. A late callback cannot exchange or create against the abandoned intent. A new confirmed attempt may then begin. This safely handles cancelled, denied or expired navigation before provider IO; an admitted exchange remains review-only even if creation was never observed.

Setup returns `authorization_pending` with an attempt identity only when that unsent state is proved by SQL. The production UI requires explicit retirement intent and confirms the saved result before enabling a new Google connection. Origin, CSRF, request admission, fresh actual session and database permission/recovery checks apply to the retirement POST. A lost outcome prompts a saved-status check. No provider request or automatic sharing consent occurs during retirement.

The migration also corrects both code-exchange admission commands to acquire the same global provider budget before insertion and to recheck provider/attempt expiry after waiting for that lock. Counting exchanges alone did not previously enforce their admission limit. The production initial callback now requires the versioned `budgeted_google_calendar_creation_exchange` receipt with `admissionVersion:1`; older/unbudgeted SQL cannot authorize token IO. Synthetic legacy paths remain separate. No Google token is stored in the restart journal, operation or audit result.

The new journal's nonsecret business history must be included in the current source/export/recovery adoption. Private ephemeral session details and credentials must remain excluded from portable product exports. Full restore must preserve abandonment and prevent reuse of stale OAuth links. ## Reconnection identity

The original creation reconnect fence cannot be relaxed merely because a new access token can read the existing calendar. A shared calendar may be accessible by another account. Migration 128 establishes the original signed provider identity; migration 129 below uses that binding for the same-account comparison and renewed consent. Legacy grants have no proved provider subject and stay review-only. Reviewed email and Calendar `dataOwner` metadata are not substitutes for a verified account identity.

Google's [OpenID Connect documentation](https://developers.google.com/identity/openid-connect/openid-connect) provides its authentication protocol and nonce/ID-token validation requirements. Its [server-side ID-token guide](https://developers.google.com/identity/gsi/web/guides/verify-google-id-token) identifies verified `sub` as the stable account identifier and requires signature, issuer, audience and expiry verification. Require that same subject during reconnect; never trust decoded claims, email or a browser-supplied identity. Legacy grants lacking that proof must remain review-only rather than being silently upgraded. Migration 127 added no identity scope or reconnect permission; migration 128 added initial identity binding while reconnection remained closed on that source.

## Decision: verify the original Google account during initial authorization

New production authorization requests exactly `calendar.app.created openid`, with `include_granted_scopes=false`, offline access, explicit consent, PKCE and a per-attempt nonce. No profile, email or wider Calendar scope is requested. The UI explains that Google confirms the account being connected. This is integration identity proof; Crest still requires its own genuine authenticated owner/session and explicit disclosure/sharing/notification consent before any appointment sync.

The nonce is derived with a distinct domain from the secret sealed PKCE verifier and its complete attempt/business/actor/session/epoch/generation/client binding. The callback reconstructs it only after one-use state consumption and verifier decryption. The token adapter verifies the issued exact scope set, then verifies Google's RS256 ID token using the installed `jose` verifier and a fixed HTTPS Google public-keys endpoint. Signature, issuer, single configured audience, authorized party when present, subject, bounded issued/expiry time, nonce and access-token hash when present must agree. Token-selected key URLs cannot select a remote host. Public key responses are bounded to 64 KiB/32 keys; retrieval has a three-second deadline, five-minute cache and thirty-second unknown-key cooldown. That public infrastructure request carries no credentials, cookies or account data and has its own bounds; business token/Calendar calls retain committed shared-budget admission.

The verified issuer/subject and exact identity-enabled scope are sealed with the private grant, under the existing credential version/AAD binding. Refresh keeps the verified account identity when no new ID token is returned; a returned ID token must verify for the same account. Omitted replacement refresh tokens preserve the prior token. Legacy credential payloads remain readable under their original strict six-field profile; unexpected identity scopes/tokens cannot silently upgrade them. ID tokens themselves are not retained or returned to the browser.

Migration 128 atomically links the verified original issuer/subject/client to the initial destination, credential, creation attempt, owner and recovery epoch in an append-only, RLS-protected account-binding table. Promotion still uses all original owner, creation-result, current-key, deadline and sealed-envelope checks in the same transaction. Failed identity binding rolls back promotion; no guessed backfill is performed. The database's existing Calendar-scope column/AAD purpose still identifies the Calendar API authorization component; the complete issued scope and identity are authenticated in the sealed grant and validated by the server. The provider subject is not an access credential, but remains private from ordinary web/OAuth-role direct reads.

## Decision: verified reconnect and renewed sharing consent

Migration 129 implements those coupled boundaries. A private fresh-owner/permission/recovery-authorized target command derives the saved destination, current generation and immutable original Google subject/client. It refuses missing legacy proof, pending/unconfirmed revocation, or a generation with an already admitted exchange. The reconnect POST requires explicit owner intent and the configured account, compares the requested destination/generation to that private target, records the existing destination review and starts fresh one-use state/PKCE/nonce authorization. Browser responses omit the private provider subject. The callback selects initial creation only when SQL proves no destination; otherwise it uses the private current target and a reconnect-only callback. No callback/browser field selects a generation or a calendar.

The admission trigger now permits an identity-verification exchange for an originally created calendar only with its original account binding and a current matching destination review. This is permission to verify a new token, not to adopt its account. Exchange budget admission is versioned and committed. The signed new subject must match the original issuer/subject before even reading the calendar, and verified destination identity must still match the saved target. A mismatch remains review-only with its retained exchange; no new calendar, credential staging or consent is produced. Legacy unbound created calendars retain their refusal. There is no guessed subject, deleted claim or blind retry.

The verified staging command rechecks actual owner/session/recovery authority, original account/client binding, committed exchange/destination verification, current generation/key/deadline and sealed credential binding. Its immutable reconnection journal links the attempt, credential, intended generation, owner/session/epoch and provider identity. A committed operation and audit event record the staging. This does not activate the new grant. Reviewed-consent commands derive the activation generation from the exact original verified staging or reconnection journal; a new payload, sharing and notification review is required. Latest consent/generation and current keys must still agree when confirming. Consent history remains append-only, and receipt/status lookup compares the actual saved generation rather than assuming generation one. Pending staging takes precedence in setup state over an earlier active generation.

The settings UI offers explicit reconnection of the saved calendar, waits for confirmed earlier revocation where required, and routes the owner back to the sharing review. Interrupted review references now use connection-scoped tab keys. Valid legacy references remain recoverable for their original context; a different connection's uncertain reference is preserved rather than overwritten or falsely treated as the new consent. Private UI state clears on hide, sign-out or authority failure. Actual release acceptance, provider/device behavior and current source/export/recovery adoption remain required.
