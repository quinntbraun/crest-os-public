## Scope and decisions

Schema11 adds read_authorized_business_context, a single allowlisted security-definer read of actor ID, selected business ID, currency and timezone. It requires identity.read from the active membership's existing migration-maintained role mapping. It never returns the recovery epoch, writes_enabled, a permission list, credentials/ciphertext, legal name, customer or financial records. A context object is point-in-time data, never authority for another query, mutation, export or subsequent request. This avoids introducing a generic trusted context/GUC or positive table RLS policy before its consumers and tests exist.

The server-only createTenantContextReader composes the existing real SDK/JWT/live-provider/local-session lifecycle first, with a25second overall bound, then passes only the verified exact local session/actor/issuer/subject/provider-session/expiry and hashed opaque credential into the fixed parameterized routine. The existing restricted connection guard, three-second single-query connection bound, statement/lock limits and production TLS verification remain. No caller-selected SQL or identity/capability argument is exposed. The compiled Node application exports the reader for explicit trusted composition; no HTTP route, default executable switch or UI business access is added. A future route must still supply Origin/CSRF/admission and its complete route-specific permission/recent-auth/audit requirements.

The routine validates READ COMMITTED isolation and complete typed inputs, then holds actor, business, recovery-authority and local-session shared row locks in that order. Actor-before-business agrees with existing identity mutation ordering. Membership changes take the business root exclusively; the read does not lock membership first and create a lock inversion. The final metadata SELECT is a fresh statement after waits. It rechecks the exact hash and all bindings, live owner/security epoch, nonrevoked local encrypted-token presence, original absolute/idle limits, provider expiry, business status, active membership, identity.read mapping and recovery-root presence. A separate fresh narrow auth.sessions check rejects provider removal, MFA downgrade or provider deadline expiry. The signature/issuer/audience SDK check remains mandatory in the server reader; synthetic provider rows used by DB invariant tests alone are not authentication evidence.

This is a background preparation read. It preserves authenticated/activity/expiry timestamps and does not enable writes, create operation/audit records for nonexistent domain changes, expose an epoch that a stale command could auto-upgrade, or rotate authority. Reads can inspect setup/active business context while writes_enabled remains false. A suspended business denies. Locks last until the read's SQL transaction completes; in-flight authorized reads may finish before a waiting revoke/change commits. Subsequent requests reauthorize. Already-delivered data cannot be retracted. Provider signature expiry and revocation can still occur after their last check; there is no distributed atomic transaction with Auth.

Reuse the existing restricted nonlogin session owner for this authentication-context routine. Add only SELECT(currency,timezone), SELECT(membership.role), SELECT(role,capability), and SELECT(recovery.id,business_id) plus lock-only UPDATE(recovery.id). Recovery's false WITH CHECK policy and existing immutable identity/version triggers prevent actual updates. No web/worker/browser table access, recovery capability, schema CREATE, membership, superuser or bypass privilege is added. Default-grant/role/forced-RLS drift checks precede DDL; revoke PUBLIC execution and grant only crest_web. No new database role, table, persisted context cache, crypto format or dependency is required. Original10 migrations and canonical baseline bytes remain immutable; append a checksum entry and increase only the schema compatibility ceiling.
