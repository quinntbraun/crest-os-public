# Canonical financial posting verification after restoration

Receipt-root and range checks do not replace the complete registered posting
rules. The isolated restored-finance verifier now reuses those existing rules
instead of implementing a second version of every invoice, payment, correction,
tip, refund, collection and supplier-payable posting contract.

## Boundary and authority

This is an offline destination-verification component. It is not a backup
reader, scheduler, web endpoint, repair tool or incident authorizer. It creates
no login, membership, grant, role, data record or routine. The caller supplies
an already connected dedicated idle direct/session PostgreSQL client with
verified production TLS and independently established recovery authority.

The source/scheduler backup reader keeps its exact existing permissions. It
cannot run application security-definer routines. Destination verification
uses a different temporary offline identity: NOINHERIT, no administrator/bypass/
creation/replication powers, one SET-only membership in the existing nonlogin
crest_finance_integrity_owner group, and read access to the migration register.
The identity must have no ordinary table-write or schema-create rights. The
group itself has powerful integrity functions and some write capabilities;
these credentials must be confined to the independent fenced restoration,
never installed in the source, app or scheduler, and retired after review.
This is an explicit operator configuration requirement, not a new runtime grant.

The tool forces read-only transactions and bounded query/operation lifetimes.
Only inside its read-only repeatable-read snapshot does it SET LOCAL ROLE to
the integrity group. It never commits data, posts money, repairs a record or
replays a command. PostgreSQL read-only enforcement remains active even inside
security-definer calls. The transferred client is closed on every outcome.

## Independent code baseline

Before executing any application routine, the tool compares all application
routine definitions, owners and effective ACLs against the independent reviewed
baseline. The catalog includes crest, crest_private and crest_commands; hashes
use PostgreSQL17 pg_get_functiondef with a fixed catalog search path and stable
name/signature ordering. Effective owner/PUBLIC/explicit grants are sorted by
names, not installation-specific OIDs. Unknown routines, altered code/settings,
owners or grants change the digest and refuse execution.

Baseline138 was generated by applying the exact checksum-verified138 migration
registry to a separate empty PostgreSQL17.11 fixture, not by learning from the
database being restored. It has1269 routines and digest

The registry is pinned to9d4864f71e8641a6972b4a5db4b1e47bf58f3917ebab34f27e1802226d72236a.
The generated record is retained at `.local/recovery-routine-baseline138/result.json`.
Future schema changes require an independently reviewed new baseline; never
overwrite this one to make a differing restore pass. Different server deparsing
or deployment defaults can require review, not automatic acceptance.

## Data binding and checks

A private WeakMap binds the actual successful restored-database comparison to
its point, migration list, nonlogin role state, event count/fingerprint and
destination endpoint/server start. A copied JSON success object is rejected.
A new process must authenticate/recompare the point before obtaining that
capability. No password or raw connection URL is retained in it.

The new snapshot must match that endpoint, migration list and role state before
code execution. After assuming the integrity role, the exact financial-event
multiset must match the successful comparison using the existing PostgreSQL17
JSONB row-hash algorithm and serialization settings. Every event across all
captured businesses is then checked through the canonical
crest_private.verify_finance_event_posting dispatcher. Missing source/audit,
incorrect lineage/components or an unsupported posting fails under the existing
registered rules. The event multiset and exact checked count are compared again.

The previous data comparison and this posting verification use separate
snapshots; output explicitly says atomicWithDataComparison:false. Physical
destination isolation, network/credential fencing and controlled reopen remain
operator/incident acceptance. Full source-to-event completeness, AR/AP/funds/
money/global reconciliation, openings, bank/custody controls, table constraints,
triggers/policies and complete security acceptance are not established by the
routine catalog alone. All results retain fullBusinessReconciliationVerified,
securityAndIncidentAcceptance, runtimeActivated and completeBackup as false.

## Executed acceptance

Native44/44 on e0304c1 passes with tracked source unchanged and owned cleanup
awaited in `.local/recovery-restored-finance138/result.json`. The fresh recovery
process applies the actual authenticated dump, obtains a genuine complete data
comparison, then uses a new restricted offline finance login for all four posted
events: invoice, receipt, unapplication and fund application. The independently
generated1269-routine catalog matches the restoration exactly before execution.

A copied comparison capability is refused. Replacing the dispatcher with a
routine that raises an execution marker is refused at catalog before that code
can run. Changing a restored payment's confirmation while exact journal debit
and credit totals stay unchanged is refused at postings by the canonical source/
audit contract. Restoring the original routine and payment makes all four events
pass again. These fault injections exist only in the separate disposable target;
source records remain unchanged. Prior range/original/journal refusals and full
artifact/object/configuration cases remain passing. Types and targeted lint pass.

This fixture exercises the populated four posting families above. Other posting
families retain their registered tests; this run is not fresh restore acceptance
for every family or the remaining global/security/physical recovery gates.
