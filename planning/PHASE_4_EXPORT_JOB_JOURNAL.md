## Original command and receipt boundary

`src/security/source-export-job-contract.ts` defines the data-only shared boundary for request, claim, expire and stop. Each command retains its complete original business, operation, recovery epoch and job IDs plus the frozen release/profile/schema for requests or expected version and lease for transitions. These are small non-PII references; a future pending store must preserve them exactly across interrupted requests and deployments. Never replace an uncertain original command with the current release/epoch or new IDs. No pending store, transport, owner screen or dispatch is implemented here.

Every immutable receipt contains exactly schemaVersion, command, job and auditEventId. The database independently reconstructs the retained command from its immutable operation and audited before/after projection. In particular expiry retains the original lease in command even though the resulting job clears its lease. The shared parser binds the receipt to that exact original command and authenticated recording actor, validates all22 projected columns, preserves bigint versions and UTC microseconds, and checks the allowed resulting state. An explicit current-owner stop may retain an older job epoch or creator; its operation epoch and recording actor still match the original stop command. A historical Running receipt proves no current lease, session or download authority.

Sixty-six focused unit cases cover closed shapes, copied/frozen values, original-reference and actor mismatches, exact version advancement, expiry lease binding, historical stop provenance and invalid source state/timestamps. Each committed result in the native command wrappers now passes this independent parser, and all five expiry cases reject a different original lease after an actual database lookup. Genuine database execution must still accept the corrected source.

## Original encrypted intents and separate verification facts

The unregistered `proposals/source-export-parts.sql` follows jobs and snapshots in the same forward43 candidate. It adds forced-RLS append-only export_part_intents and export_part_verifications. Two fixed commands record an original intent or its separate verification; raw web SELECT/INSERT/UPDATE/DELETE, helpers, generic stage choice and ownership remain unavailable. Reuse the existing closed command/session owners and all fresh provider/local-session/recent-owner/export.bulk/recovery/live-lease checks on every call, including a historical replay. Lock the job before deciding sequence or writing facts and recheck authority/expiry after waits and before acknowledgment. Network I/O remains outside all database locks.

One immutable intent is bound to a part UUID and ordinal in the already frozen original plan, exact business/job/actor/epoch/lease/generation/plan hash, safe filename/MIME, original plaintext length/hash, scoped object key, key ID and original ciphertext length/hash. Retain its complete original request text (maximum8192 UTF8 bytes), exact SHA256 and the audited claim operation as provenance. Validate closed nested JSON and duplicate keys before conversion, positive exact integral byte counts with8MiB plaintext/16MiB ciphertext limits, declared original file bytes/hash and the exact exports/business/job/generation/part.jwe namespace. Persist no keys, plaintext or ciphertext bodies. INSERT guards independently validate projected metadata; table constraints and FKs bind source/provenance and original-byte hashes. Updates/deletes/truncation remain refused.

The next intent is allowed only when all earlier planned ordinals have separate verification facts and no unverified intent remains. This keeps the separately planned source manifest last. Replaying an existing byte-identical intent does not create a new upload candidate or advance sequence. Changed key ID, ciphertext bytes/hash or original root spacing cannot replace that original. This acknowledgment is not a provider PUT capability and grants no permission to retry an uncertain write. The existing store still permits one attempt per prepared candidate and conditional immutable writes; reconciliation reads the original ciphertext intent explicitly, without generating replacement bytes.

A verification row is distinct from the intent and requires its exact original request bytes/hash, matching claim/plan metadata and the next valid ordinal. The database stamps verified_at/created_at together and retains the original audited lease operation. Idempotent verification does not rewrite either timestamp or history. A previous success does not bypass a later session, membership, recovery or lease refusal. Routine part progress creates no new generic operations/audit entries; these immutable facts are anchored to the existing audited claim, avoiding a pair of large general-history entries for every file.

Verification is a trusted server attestation, not a cryptographic or HTTP proof produced by PostgreSQL. Only the future server adapter may call this command after the actual store has independently read, hashed, decrypted and checked the original binding/bytes; never expose it as a browser-submitted claim of success. Direct native metadata tests exercise the database protocol without claiming actual object custody. The six composition/fault cases separately combine real SQL commits, real AWS SDK SigV4 HTTP and standard JWE against local synthetic object storage. They verify committed intent visibility before each PUT/GET, exact original ciphertext and decrypted bytes, separate verification only after successful reads, lost committed PUT with explicit original-only reconciliation, changed recovery authority during a real GET, corrupted read/no sequence advance, and injected caller acknowledgment loss after real intent/verification commits. The injected acknowledgment-loss cases are explicit caller faults, not claims of a dropped PostgreSQL TCP response. No hosted provider conformance or full worker dispatch is claimed.
