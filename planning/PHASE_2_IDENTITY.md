## Schema and identity decisions

Schema ordinal2 is migration20261021032954. Six relations belong to the non-login schema owner, all with enabled AND forced RLS and no policies or positive runtime grants: `crest.businesses`, `crest.memberships`, and `crest_private.actors`, `business_recovery_authorities`, `role_capabilities`, `identity_events`. Internal trigger helpers use invoker security, fixed pg_catalog/pg_temp search paths and no PUBLIC/runtime execute. They do not provide a bootstrap or generic CRUD endpoint. Future command-owner policies and narrowly scoped grants require separate reviewed migrations.

Actors are durable global UUIDs, independent of provider tables. An owner requires a nonempty immutable issuer/subject pair; it is unique as a pair, with no email field, provider FK cascade or automatic membership. A named system actor cannot be an owner member. Migration seeds only the powerless `security_bootstrap` technical actor and owner capability names. It creates no tenant, owner, provider identity, session, credential or active write authority.

The initial permission names are identity.read, identity.manage, crm.manage, finance.post and export.bulk. Mapping names to the V1 owner role is data, not a positive SQL grant or an authorization API. Incident recovery authority is intentionally absent from this ordinary mapping. Every future route/command must check a verified live session, active actor/membership, named capability and business scope. Provider/credential checks cannot be replaced by this metadata.

Businesses use USD and a validated PostgreSQL/IANA timezone name. Technical states setup/active/suspended describe identity availability; they do not enable production, financial features or writes. A business must commit with a live owner and exactly one recovery-authority row. Its default writes_enabled=false is deliberately closed. The recovery UUID is independent of an actor's session-security UUID. No normal write or incident rotation routine exists yet; the transaction-held recovery fence and operation/audit framework remain prerequisites to the first domain command.

All mutable rows carry versions, creation/update actors and server timestamps. Creation identity/provenance, tenant association and provider binding cannot change. An update must advance version exactly once; future commands must additionally compare the caller's expected version. Tenant creator/updater references use composite membership FKs, including initial self-membership in one atomic provisioning transaction. Historical membership rows remain after deactivation so attribution survives. Nullable operation/import IDs are reserved provenance, not a claim that their future command/import frameworks exist. Active config references and operator/finance controls remain downstream migrations.

## Last owner and concurrent administration

Every committed tenant retains an active owner membership whose durable actor is enabled. Deferred checks allow atomic controlled owner replacement/provisioning, while rejecting ownerless final state or a missing recovery root. Membership changes lock the actor FOR SHARE before locking the business root FOR UPDATE. Actor changes lock affected business roots in UUID order; deferred checks lock/recheck roots again. This handles concurrent member removals, actor disable versus removal, and a new membership racing a disable. Locks remain held through commit. Do not remove an FK/lock to make a test pass.

These identity mutations require READ COMMITTED and reject snapshot isolation: their proof depends on fresh snapshots after waiting for the root lock. Future administration commands must follow this actor/root lock order, use bounded waits and handle deadlock retries under the canonical protocol. This identity administration lock is distinct from the shared business recovery-authority fence; it is not a replacement for that fence. No network call belongs inside these transactions.

## Identity history and access boundary

`identity_events` is a global technical identity trail, separate from future tenant business `audit_events`. Nullable business_id is limited to global actor/capability history. It records database principal plus claimed creation/update actor, operation identity, versions and explicit before/after field projections, atomically with the change. The authenticated actor assertion must be supplied by future verified administration commands; privileged synthetic SQL is not evidence of owner authentication.

The payload has schemaVersion1 and an explicit field allowlist, so a future secret column cannot silently enter history. A SHA-256 digest covers the PostgreSQL17 jsonb text representation of the complete event payload, including event/actor/entity/principal/time metadata. This supports integrity verification, not external anchoring, administrator-proof history or a general cross-runtime JSON canonicalization contract. All identity roots/history reject DELETE/TRUNCATE; permission mappings and events also reject UPDATE. A migration administrator can still alter DDL. External recovery/audit preservation remains required.

Before object creation the migration revalidates the five restricted roles and rejects unexpected owner default grants, including per-schema provider grants. The API remains disabled with no exposed schemas; web/worker/recovery/anon/authenticated/service roles cannot read these relations or invoke the helpers. A table owner still sees zero rows under forced RLS. No provider token, cookie, password or real record belongs in these tables/tests in this stage.
