## Transport and request decisions

transportFromIncomingMessage captures Node's actual IncomingMessage socket address, TLS encrypted flag and raw Host/X-Forwarded-For/X-Forwarded-Proto occurrences. Frozen nominal evidence lives in a private WeakMap and refuses JSON serialization; a browser Request/header/JSON object cannot manufacture it. Only the trusted server adapter may call this function. Evidence contains no authentication or tenant authority. The shared literal-IP normalizer preserves existing HMAC domain/output semantics, including IPv4-mapped IPv6 normalization; no admission key rotation or database migration is introduced.

The resolver snapshots configured canonical Origin, environment, mode and an explicit allowlist. Every request URL and exactly one transport Host must match that Origin. Production requires actual TLS on the immediate socket, even if a forwarded header claims HTTPS. Loopback HTTP remains test-only; production cookies retain Secure. Direct mode ignores all forwarding claims and uses the socket address. Proxy mode additionally requires an allowlisted immediate peer, exactly one https protocol claim and exactly one X-Forwarded-For field. The entire chain is limited to1024bytes/eight literal IPs. Walk from the right through explicitly trusted peers and use the first untrusted address; a forged prefix to its left cannot select the budget key. Unknown/missing/ambiguous/all-trusted/malformed chains deny. At most16 distinct literal peers are configured; hostnames, broad implicit trust, automatic provider inference and alternate Forwarded/X-Real-IP/CDN fallbacks are unsupported.

This proxy profile requires a verified proxy that strips or correctly appends client forwarding claims, a restricted origin network path, and encrypted proxy-to-application transport. A peer IP alone does not attest a proxy's header behavior. No existing Render forwarding contract, TLS termination/uplink, network isolation or addresses are presumed verified. This is a conservative supported profile, not a claim that the planned hosted platform already satisfies it. Research and demonstrate its actual ingress or explicitly review another proven transport profile before deployment. No platform/provider switch is selected here.

createAuthenticationHttp constructs the existing actual browser flow internally; production callers cannot inject a weaker flow callback. Only POST /api/auth/bootstrap, /api/auth/login, /api/auth/session and /api/auth/logout dispatch, with no query/hash or alternate schema/action field. Unknown paths return private404; unsupported methods return private405/Allow:POST, without CORS or preflight permission. Other denials return the same fixed400 body. Socket/URL validation precedes body/flow IO. Bounded JSON/cookies and exact Origin/fetch-site checks precede flow IO; login requires its pending cookie and other session operations require the app cookie. Existing single-use CSRF/login/IP limits, mandatory ordinary proof admission and separately bounded CSRF-protected logout are reused. All response bodies/cookies use the previous explicit private serializers and deny-all JSON CSP. Provider tokens/evidence/passwords, raw request headers/IPs and exception details are never reflected or logged.

An outer35second signal bounds body plus flow work; body retains its five-second limit and flow its30second limit. Cancellation is checked before work, after issuance and after response construction. A newly issued login is tracked separately from proof reissue. If its response construction/cancellation fails, discardUnexposedLogin uses a fresh four-second cleanup budget and the existing local-first logout. This server-only method accepts only an object actually issued by that same flow, never a raw browser credential, another flow's result or a session-proof wrapper; it does not spend endpoint admission. Cleanup failure still returns a generic response with no credential. Existing sessions are never revoked merely because a proof response fails. Cleanup is best effort when the database/provider is unavailable; durable orphan reconciliation remains a production gate.

Returning a Response is the dispatcher's handoff boundary, not proof of delivery to a browser. Atomic replacement may already have revoked the previous cookie before a response is lost. A production adapter still needs bounded headers/connections/body delivery, disconnect propagation, response-write failure handling and eventual orphan cleanup; HTTP cannot atomically commit both database state and client receipt. Abandoned bootstrap contexts retain their existing bounded TTL/admission cost. Do not refund uncertain outcomes or silently reinstate a replaced session.
