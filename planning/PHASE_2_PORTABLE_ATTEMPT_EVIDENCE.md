## Decision and scope

Use a small Node24 utility with only node:crypto and no PostgreSQL, React, server-only, network, filesystem, environment or application-configuration dependency. No new library, DB migration/grant, HTTP/UI/CLI/scheduler, source writer, automatic scanning or runtime composition. This is a bounded supporting evidence format within the existing versioned JSON/independent-reader contract and ADR36, not a replacement for EXPORTS_AND_BACKUPS2's authorized repeatable-read complete export protocol. No canonical amendment or business-rule change.

verifyProviderAttemptEvidence(serialized,expected) accepts a UTF8-representable string capped131072 bytes and separately supplied expected actor/attempt UUIDs/exact issuer (1..500 Unicode code points). Normalize only the expected UUID spelling. File header UUIDs and original evidence UUIDs retain the database's lower-case representation. Reject unpaired UTF16 surrogates and NUL rather than silently replacing source bytes during UTF8 hashing. All errors are fixed PROVIDER_ATTEMPT_EVIDENCE_REVIEW_REQUIRED without parser messages, contents or causes.

## Version1 selected fragment

One JSON object per line, LF or CRLF framing, optional single final newline, no blank lines/BOM/trailing garbage. Header has exactly format=crest-provider-attempt-evidence, formatVersion=1, actorId, providerIssuer, attemptId. Follow with1..6 flat record envelopes, each exactly kind, canonicalEvidence, evidenceHash. Kind is one of start, target, registration_finish, stop, request, outcome, at most once; a start is required. Record order is arbitrary and output order is fixed to that list, not an asserted chronological event order. Header and envelopes are packaging only, never database canonical evidence. canonicalEvidence is a JSON string preserving the original ledger text; JSON serialization of the envelope escapes that string without changing its recovered UTF8 bytes.

Each original body is capped8192 UTF8 bytes. Verify SHA256 over that exact string, without JSON reserialization, whitespace/key-order normalization or RFC8785 claims. Standard JSON parsing plus a bounded flat-object check accepts only scalar/null values and rejects duplicate member names, including escaped equivalent names, in header, envelopes and source bodies. Flat source bodies use only the exact current schema1 field allowlists from migrations20..24. Unsupported fields/version/shape require review; no token/cipher/credential/raw payload extension is accepted. Maximum20 fields per flat object. Validate schema1/system, UTC finite four-digit AD timestamps (including actual calendar dates), valid target time range, UUIDs/hashes, principal1..63 UTF8 bytes and exact actor/issuer/attempt binding. Preserve Unicode, escapes, whitespace and six-digit timestamp precision in original strings.

All included records must share original actor, security epoch, issuer, subject and reserved app ID. Included provider IDs match the signed target where supplied; distinct finish phases have distinct IDs and the same original registration source when both are present. Registered stopped evidence requires its recorded local revocation; an unregistered stop retains null registration/revocation. A request requires included target and stop, exact original target/finish hashes and stop ID, pending_review state and coherent optional registration/cleanup-reference/revocation fields. An outcome requires the original request, exact request hash/ID/source finish and distinct provider_removed or provider_absent_observed outcome. A stopped unknown target may be followed by a later signed target/request/outcome without rewriting its original null fields. No timestamp ordering is invented as an event sequence, and principal metadata is not a signature.

Return frozen metadata, fixed-order frozen copies of original record envelopes, missingKinds and assurance=internal_consistency_only. Missing kinds mean omitted from this fragment, not absent from the database or safely resolved. Even all six included kinds do not establish a complete security export: registration-event/cleanup-reference originals, inventory observations, app/provider state, other attempts, migrations/roles/configuration and recovery keys are outside this format. Source reference IDs remain references; their external original bodies still need authorized complete export/restore validation. Selected immutable records may have been collected in separate statements; the file claims no shared snapshot, as-of completeness, durable scan/Ready marker, current provider absence, external work ending or global orphan freedom.

Matching hashes and identities establish self-consistency only. A coherently forged/rehashed file can pass; this is not independent provenance/authenticity attestation or a cryptographic signature. Future private export/backup manifests must supply their own trusted custody/checksum/source context and complete coverage. Never feed this result into cleanup execution, fresh authorization or a database restore as permission. Existing live SQL source validation remains mandatory. There is no importer, restored-row writer, cleanup-request selector or migration fallback.
