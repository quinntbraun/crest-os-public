## Decision, privilege and execution

Use one fixed database operation, execute_provider_cleanup(requestId,expectedActor,configuredIssuer), in the same PostgreSQL database as the pinned Auth schema and Crest evidence. The caller provides no provider UUID, subject, token or broad logout scope. New crest_cleanup and crest_cleanup_owner roles are nonlogin/noninheriting/noprivilege with no memberships; unexpected prior role ownership/grants/defaults/configuration are refused. No service principal/login or scheduler/endpoint is provisioned. Only the owner gets provider session ID/user-ID SELECT and session DELETE, provider migration-version SELECT, safe Crest source reads and outcome SELECT/INSERT. PostgreSQL17 MAINTAIN on the two pinned cascade children permits ROW EXCLUSIVE locks without child secret SELECT or child INSERT/UPDATE/DELETE. MAINTAIN has physical-maintenance powers not exposed by any fixed routine; this explicit tradeoff fences schema DDL without granting child data access. The ordinary caller can execute only the fixed command, not assume the definer or access tables. Web, worker, recovery, inventory and provider roles cannot execute it.

For a new execution, confirm the selected request's actor/configured issuer, exact stopped finish and original target/attempt/epoch/subject/source hashes; match immutable actor binding even when disabled/old-epoch. Check any reserved app registration is the same actor/epoch/provider, originally CREATED for that attempt, already revoked and has its existing schema17 cleanup reference. A later different app, live/conflicting source, original-request/source discrepancy or provider UUID now belonging to another subject rejects without deletion. Share schema22's nonwaiting producer lock, plus a domain-separated request execution lock. Ordinary issuance remains fenced; privileged historical/admin paths are outside that producer contract and need operational draining/review.

Before provider inspection, hold ROW EXCLUSIVE locks on sessions, refresh_tokens and mfa_amr_claims through transaction end. They allow ordinary provider writers while excluding FK/trigger/table-shape changes; unknown dependencies/triggers never get adopted after inspection. Fresh review requires the pinned Auth migration watermark20260831180000, ordinary nonpartitioned/RLS tables owned by supabase_auth_admin, UUID/not-null ID+subject and ID primary key, exactly the two validated nondeferrable session-ID ON DELETE CASCADE child FKs, no grandchildren/inheritance/rules or noninternal triggers. Review at migration apply and every new execution; unsupported provider versions/permissions stay blocked. Coordinate/drain provider/admin upgrades and review each new provider version; this is not protection against a malicious privileged DB operator or arbitrary namespace rewrite. Actual hosted operator support/permission is a production gate, not established by synthetic CI.

DELETE only the derived session with the derived subject. The actual provider row lock and DDL-lock waits are bounded2seconds; other request/lifecycle overlaps return busy immediately. READ COMMITTED rechecks the subject predicate after row waits. A zero-row delete with a still-present session is a conflict/review, never an absence claim. The upstream provider's pinned refresh-token and MFA-AMR cascades run without granting the Crest owner child-table data access. No Auth user/factor or another device is selected. No encrypted tokens, key IDs or credentials are restored or retained after local revocation.

## Atomic evidence and recovery semantics

provider_cleanup_outcomes is append-only, forced-RLS, owned by crest_schema_owner, one outcome per original request. Its invoker trigger performs fresh review/removal and derives every body/provenance/hash field even under privileged direct INSERT. Provider deletion, cascades and outcome append commit together; injected append failure or rollback restores all. The evidence links original request hash, source finish, actor/original epoch/issuer/subject/provider/app IDs, provider_removed versus provider_absent_observed, UTC observation/recording time and database principal. No provider secret, credential digest, JWT, refresh material, contact, code, password or raw diagnostic. Original UTF8 JSON and SHA256 are portable byte checks, not signatures or tamper-proof attestation.

Exact committed execution returns the original bytes/hash without touching provider state, including after provider reappearance or schema changes. Wrong actor/issuer rejects. An absent historical lookup may race an uncommitted transaction; it does not authorize new identity or a new request. Same original request is the sole replay identity. The isolated inventory caller gets only a fixed scoped historical outcome reader, including read-only access; no raw table, execution or provider mutation grant. Original request remains pending_review as selection history; the separate outcome never rewrites that fact. A later authorized security export/backup must preserve both ledgers and all original referenced bytes; customer exports gain no global security access. No purge/retention deletion is added.

provider_removed is a transactional row-removal fact. provider_absent_observed is a distinct point-in-time absence observation. Neither proves global orphan freedom, all external I/O ended, current eligibility, HTTP logout/cookie delivery, or cryptographic invalidity of an unexpired signed JWT. Crest still checks fresh provider/local state. The adapter does not fabricate provider HTTP audit entries; the immutable Crest outcome is its audit. Immediate best-effort scoped SDK logout remains unchanged. This first executor covers only schema23's proven stopped target; ordinary logout-only, unknown/in-flight, unfenced historical/enrollment cases are not silently selected. No automatic timeout closure, broad-user logout or generic UUID deletion API.
