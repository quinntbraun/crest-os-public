## Decisions

Refresh uses the installed official Auth SDK and JOSE. The encrypted prior access JWT supplies a private, signature-verified reference for the original password/TOTP instants even after JWT expiry. Its issuer, audience, subject, provider session, role, AAL2, anonymous flag, header, chronology and AMR remain strictly checked. It cannot produce authentication evidence. The replacement must pass normal current JWT expiry/signature/claims, online confirmed user/verified TOTP and actual live provider-session checks, with exactly the same password/TOTP instants and identity/session binding. A new iat never becomes recent authentication.

Verification refreshes when decoded access expiry is within60 seconds or past. This is a scheduling hint only; decoded data never authorizes access. Explicit server refresh is also available. After rotation the lifecycle performs ordinary live verification and a final database reread without recursively refreshing a short-lived replacement. Neither path returns access/refresh tokens. Browser-facing CSRF/origin/abuse protection remains required before exposing any refresh operation through HTTP.

The transaction runs READ COMMITTED. lock_app_session takes the actor root FOR SHARE before the session row FOR UPDATE, then returns a fresh local snapshot. Actor disable/epoch changes serialize with refresh; local revocation and competing refreshes serialize on the session. The server holds those locks through decryption, the network exchange and encrypted replacement. A waiter that observes a different version verifies the winner's current access token and skips exchange; it never submits the stale refresh token. If the winner's token has already expired, the waiter denies and a later request may retry against current state.

replace_session_tokens rechecks the expected version, actor/epoch validity through the snapshot, absolute local expiry, trusted168-hour inactivity and actual live AAL2 provider session using a fresh database clock. It updates only ciphertext, key ID, version and provenance. Database triggers retain immutable session identity/hash/trust/creation/authentication; no UPDATE privilege is granted for expiry, reauthentication, activity or revocation. Encryption uses the configured active key and immutable session-bound JWE additional data. Routine same-key refresh creates no repeated authentication/activity event; a key change appends the existing safe security projection without token/hash/ciphertext/key metadata.

Both functions have fixed pg_catalog,pg_temp search paths and row_security=on. The NOLOGIN/NOINHERIT/non-admin/non-bypass session owner receives only five additional column UPDATE rights under forced RLS. Web receives EXECUTE only, with no direct table grant. Schema7 preflight rejects owner-role, membership, table-boundary or preexisting update drift. These trusted server functions do not establish tenant authorization and cannot replace the request/transaction authorization pipeline.

The installed SDK retries transient refresh failures automatically. This exchange disables that behavior by converting a failed refresh transport/status into a generic nonretryable SDK result. A request whose single-use token may have been consumed must not be replayed after uncertain rotation. Other provider operations retain their existing behavior. The provider operation limit stays10s with3s HTTP requests. Fresh runtime connections use1s connection establishment; refresh uses11s statement,10s lock,12s query,12s idle-in-transaction and15s whole-transaction limits, with the lifecycle's20s outer deadline. PostgreSQL17 transaction_timeout additionally bounds an orphan transaction. Ordinary lifecycle SQL keeps the existing shorter limits.

Cancellation or database connection loss aborts provider work and closes/rolls back the transaction. Once an exchange has been attempted, any uncertain provider/save/commit outcome triggers separate bounded local revocation, up to3s additional cleanup, then a generic failure. No positive evidence or replacement token escapes. If the database is unavailable, revocation remains best effort; this does not establish successful logout or immediate cross-system revocation. A subsequent request must still satisfy all live checks, and local cleanup requires restored database availability. A request that loses the initial lock/decryption before an exchange does not consume a token. No external side effect can be atomically rolled back with PostgreSQL.

Revocation committed first denies refresh. Refresh holding the row first can complete before revocation acquires it; once revocation commits it clears the replacement secrets permanently. A lock timeout is a failure requiring retry, never successful logout. This is a serialized ordering, not an instantaneous kill guarantee. Session evidence still carries tenantAndRequestVerificationRequired=true; downstream business transactions must hold final session/member/capability/recovery fences.
