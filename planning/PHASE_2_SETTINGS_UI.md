## Pending intent and sign-in scope

Before any new mutation the client writes and reads back one exact versioned journal record in sessionStorage under crest.business-name.pending.v1. Its only fields are journalSchema1, businessId, an opaque edit binding and the original five-field schema1 rename command:operationId,recoveryEpoch,expectedVersion,legalName. Every nested value is validated/frozen, versions remain decimal strings, the record is bounded8192 characters, and a different existing record cannot be overwritten/cleared. Storage failure blocks sending. No cookie, CSRF proof, provider token, issuer, password or authentication evidence is persisted. No localStorage, IndexedDB, cross-tab cache, generic/financial offline queue or automatic TTL deletion is introduced. This narrowly scoped per-tab name metadata is not a backup, authority or future permission to persist customer/financial payloads. Closing/clearing browser data may lose it; the UI says so. Durable server orphan reconciliation and full recovery/export still gate production.

After current CSRF and successful fresh authorized settings work, the server adds X-Crest-Edit-Binding:base64url(SHA256(UTF8('crest.business.edit.v1\\0'+businessId+'\\0'+appSessionId))). The two separators are actual NUL bytes; this notation documents the encoding, not literal backslashes. It is a non-authorizing domain-separated scope marker, not the raw session UUID, credential digest or actor identifier. It is stable for one business/app session across proof refresh and epoch rotation, differs on another session and is never accepted as authorization/input. The six-field settings JSON and command schemas remain unchanged; other responses do not expose the marker. All responses stay private/no-store/no-CORS. The retained CSRF verifier now returns its fixed snapshot ID internally; SDK/local/provider/tenant/capability checks still precede positive output. This marker prevents a browser record from being automatically retried after a different sign-in; it does not identify or authorize that account.

Reload detects a pending record and blocks new edits. It does not automatically query or resubmit it. Check save status obtains fresh proof/current context and then the actor-scoped historical lookup with the original ID. A committed record confirms the reference, not a claim that an arbitrary same-ID payload is identical; the UI requires loading current settings to review the recorded result. A valid positive write response separately confirms the exact typed request. Version/epoch/business/receipt inconsistencies remain uncertain. A confirmed result clears only the matching journal; failure to clear blocks another edit. Version conflict clears its rolled-back claim reference but preserves the proposed name for explicit fresh context review/new Save. Operation conflict and recovery-review errors never create a replacement operation automatically.

Absence is not proof that an in-flight request failed. Retry original change appears only after an explicit absence check under the same business, app-session binding, unchanged ready recovery epoch. A click reauthenticates and rereads that context again, then submits the byte-equivalent original typed values; it never updates their version/epoch or creates an ID. Changed sign-in/business/recovery/paused writes prohibit retry. Historical commit review remains possible after reauthentication or while paused, but an absent prior-session/recovery request needs manual review; this UI does not implement incident reconstruction. Only a definite input/not-submitted/denied result on the first attempt can clear its new unsubmitted intent. That result during a retry cannot prove an earlier uncertain attempt failed, so the original stays pending. Rate/network/projection/parse/cancellation errors retain uncertainty with no automatic retry/refund. No pending reference is discarded to make the UI appear available.
