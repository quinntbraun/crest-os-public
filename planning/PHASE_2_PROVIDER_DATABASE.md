# Phase 2: live provider-session database reader

2026-10-21. Owner continuation follows merged PR6, main7a8154b22390c16a39ce43b67b468553e64aac54 (main CI39604490468 passed). This implements SECURITY2's narrow provider-session reader. No canonical amendment, browser route, production credential, real data, paid service or deployment is introduced. Schema ordinal4 is append-only; the shell supports0..4. Existing app tables remain closed, without positive business RLS policies.

## Implementation decisions

The new non-login crest_auth_reader owns only crest_commands.provider_session_is_live(uuid,uuid). It has no inheritance, role memberships, administrative/bypass attributes, app-table privileges or schema CREATE. Its only provider-table grants are column SELECT on auth.sessions.id,user_id,not_after,aal plus schema USAGE. A dedicated SELECT policy permits that owner to read these fields while provider RLS stays enabled. No users, refresh tokens, factor secrets or other session fields are granted. As with the original closed roles, migration rejects privilege/membership drift. Disposable tests preflight all six roles before claiming ownership of newly created fixtures. Provider schema owner/type/RLS mismatches fail migration for review.

The helper is VOLATILE, SECURITY DEFINER, with fixed pg_catalog,pg_temp search path, row_security=on and qualified references. Only crest_web gains EXECUTE in the nonexposed commands schema. PUBLIC, browser/provider anon/authenticated/service_role, worker, recovery and general command owner gain no EXECUTE. Web has no auth schema/table access. Inputs are the trusted cryptographically verified subject and provider-session UUID pair. Output is one boolean. Null/mismatched/missing identity, deleted session, AAL downgrade and elapsed/nonfinite not_after deny. READ COMMITTED is required to prevent stale repeatable-read observations. Device sessions stay independent.

The server-only createLiveProviderSessionLookup supplies the existing JWT/SDK boundary's required callback, using already pinned pg8.23.1 moved from development to runtime dependencies without upgrades. Configuration is server-owned. Production requires certificate-verified TLS; URL query overrides are forbidden. Explicit tests accept only disposable loopback databases. Each call opens/closes a fresh connection, assumes only crest_web and rejects privileged/inheriting runtime login attributes or unrelated role memberships. This avoids borrowed transaction/tenant state. Future pooling must prove equivalent isolation; no capacity claim is made. Runtime login provisioning remains a separate reviewed step.

Connection/statement/lock/query deadlines are1s/1.5s/0.75s/2s, with a3s whole-call bound. Cancellation closes active connections, including blocked queries. Invalid IDs, transport/SQL failure and cancellation expose only PROVIDER_SESSION_LOOKUP_FAILED without driver causes, SQL values or logs. No retries or positive cache exist. The outer boundary still validates signatures, online user and MFA. The boolean cannot authorize a route or bypass local session/tenant/capability/recovery checks.

## Test evidence and limits

Fixture ordering first records the coordinator's empty schema0 bootstrap receipt, then installs the provider schema, then applies Crest migrations. This preserves the existing empty-bootstrap guard and receipt chain. A pre-existing hosted Auth database is still not a permitted coordinator bootstrap target; production adoption needs a separate reviewed protocol. Assuming the provider role also supplies its auth-first search path explicitly, since SET ROLE does not apply login defaults.

npm run test:provider-db requires disposable PostgreSQL, pinned CLI and Docker on Linux with host networking. The official Auth v2.197.0 binary applies its embedded migrations using the existing provider schema owner. Image supabase/gotrue:v2.197.0 is pinned at sha256:1736a63078f5922b198c4cbe50f80ab9a2d3b54fe8b7b6cfb2e9dc5dbbc12c6b. Official latest stable release/source4eee58f296d9698a1c2c0ae14d7a0b379c7622d3 and Docker Hub manifest were checked2026-10-21. No hosted service, SMTP, OAuth or external account is provisioned. Fixture bootstrap secret and runtime password are random RAM-only values. The test runtime login is newly created, explicitly owned and removed. No existing credentials are read or altered. Provider migration output is never echoed; known setup failures receive a safe category.

Tests cover actual provider DDL, upgrade3 with retained nonempty identity history, fresh0 and preceding2 upgrades, exact subject/session, deletion, AAL downgrade, optional expiry, independent devices, restricted owner/column grants, direct browser/provider/web SQL abuse, stale isolation, administrator substitution, invalid inputs, connection failure, blocked-query cancellation and a successful next lookup. Schema3 tests retain their immutable prefix instead of acquiring provider prerequisites. Unit tests reject unsafe configuration before IO. All existing database/unit/build/browser/accessibility/dependency/secret/container gates remain required.

Fixtures insert synthetic users/session states into the actual provider schema. They do not run the Auth HTTP server or prove real password/TOTP/recovery/refresh ceremonies. The preceding HTTP fixture is still synthetic. A real isolated Auth HTTP integration joining signed JWT/MFA, current user, this reader and local session remains required before browser access. Provider-wide timebox/inactivity/low-AAL configuration is not inferred from existence; production configuration must be reviewed against application policy, and unsupported provider limits rejected or implemented/tested before activation. Hosted compatibility, production connection, key recovery, backups and free-production reliability remain unproven. Cost remains$0.
