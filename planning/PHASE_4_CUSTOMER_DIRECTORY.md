# Customer directory core

ADR41 and ROADMAP1.6 explicitly overlap synthetic Phases3/4 construction. A real customer record is the first CRM parent, rather than a fabricated file cabinet. This slice adds the backend only. It has no customer HTTP endpoint, page, runtime activation, live provider setup or permission to use real data. Vehicles, addresses, leads, source/referral links, imports and duplicate resolution remain future coherent workflows.

## Source and command

Migration32 adds21 customer columns covering label, nullable raw phone/email, derived nonunique search hints, preference, explicit outreach opt-out, notes, customer-since date, archive reason/time, version and provenance. Unknown details remain null; empty optional preference/notes remain distinct. Shared household contacts never merge identities. No country, contact consent, customer-since date or business rule is inferred. Archiving retains history and reopening requires an explicit command. The current command only creates manual records; it cannot invent an import relationship.

The new NOLOGIN customer and integrity owners have separate narrow grants, FORCE RLS and no deletion/truncation path. Existing owners and previous privileges remain intact; additions are limited to the listed customer/helper grants. Migration adoption refuses insecure existing roles/source ownership. All31 published migrations and original canonical provenance remain immutable. The three current canonical amendments are explicitly recorded in CANONICAL_MAINTENANCE.md.

The typed save uses current provider/session/owner authorization, identity.read and crm.manage, the original expected recovery epoch, stable customer/operation IDs, optimistic version and a full append-only before/after audit in one transaction. A deferred source/audit constraint checks the exact row. Version conflicts roll back operation claims. Exact replays validate the original digest/receipt/audit. The server adapter returns private values and treats failed commit/delivery as unknown, with no automatic retry, new operation ID or substituted epoch. Independently authorized operation lookup remains readable during paused recovery; it confers no write authority.

Directory search is literal, scoped and UUID paginated (1..50); archived rows are included deliberately. History pages (1..20) preserve original actor/operation/version and source values. Every read freshly authorizes and has a1MiB bound. Successful foreground saves recheck authorization/activity after waits. The Node application exports the factory without wiring a route or enabling customer access.

## Portability and recovery

The isolated export caller has two read-only repeatable-read routines, scoped counts and a business/snapshot-bound token. Archived rows and all21 source columns remain included. The formatter validates exact rows/count/identity, emits UTF-8 RFC4180 CSV with CRLF, a reversible null/backslash/formula-prefix convention, an explicit escape map, dictionary and per-part hashes/lengths. See the emitted dictionary for decoding; a plain spreadsheet view alone is not a lossless import. Values and bigint versions remain exact. Limits (1000 rows/8MiB output) fail explicitly, never truncate. The token establishes snapshot consistency, not authorization.

There is no production export job, private download/custody flow, complete Crest export or complete-backup assertion. A future whole-export job must freeze recently authorized business scope and collect every page/count in one owned transaction. The schema coverage manifest adds the real table. The disposable PostgreSQL recovery drill captures a customer and source audit before the dump snapshot, commits a later edit during that snapshot, and must restore the earlier exact record/audit with the retained files. Independent cloud/vault, compatible configuration/keys/images, heartbeat, incident authority and complete recovery gates still apply.
