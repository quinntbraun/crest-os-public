# Supplier posting and settlement original recovery

## Root cause and decision

The shared supplier confirmation hook retained the original accrual/payment request only in mounted React state. The expense privacy boundary unmounts that state on pagehide/hidden. A genuine committed accrual followed by a lost browser reply and pagehide/access return loses its original-check control in both Chromium and WebKit on fixed1559c10. The complete original two-case diagnostic finishes0/2 at that exact missing-control assertion, with source unchanged and owned cleanup. Evidence: .local/design-supplier-posting-before/result.json and run.log. This is distinct from the earlier supplier draft fix.

Use the existing strict opaque-reference pattern for this approved V1 posting workflow: retain schema version, business, verified edit binding, original record identifier, operation kind, operation identifier, recovery epoch and original posting identifier before delivery. Amounts, dates, supplier details, bank/statement evidence, tax/duplicate reviews, reasons and command payloads stay private in memory. This introduces no schema, permission, ledger calculation, payment provider or accounting rule change.

The store rejects malformed/oversized/duplicate-key/accessor/prototype/symbol/extra-field values, unsupported kinds and invalid identifiers. It refuses another unresolved original and verifies exact write/read/removal. Different workspace, missing capability, malformed identity and changed original state fail closed with retained bytes. Current authorization and server capability/period/version/evidence/idempotency checks remain required for every lookup or posting.

Fresh-sign-in decision: the retained binding is provenance, not authorization. A newly verified session in the same business may explicitly check an opaque original using the existing server lookup. financeAccounts.post obtains current authentication and sends the current context binding; no old cookie, CSRF proof, permission decision or private command payload is reused. This follows SECURITY's per-request authorization/revocation boundary and the existing business-scoped supplier lookup contract, without changing either. A changed sign-in is stated on the recovery screen. Retrying a previously absent original additionally requires the explicit lookup/review path and new private inputs on the matching record; the normal hook still refuses a binding change without that explicit resumption. Another business never receives a lookup or reference display. There is no silent reference overwrite or automatic command adoption.

## Behavior

SupplierWorkspace checks browser reference storage after hydration before mounting editable supplier tasks. An unresolved original replaces them with one focused lookup action, privacy guidance and a collapsed original-reference disclosure. There is no automatic original lookup, new submission or replay.

A verified committed accrual releases only its matching reference and offers the actual supplier workspace. A verified payment also reads the real current register, displaying its returned date/scope and actual balances. A failed register read does not change the known committed original into an unknown payment; the UI asks for a register reload instead. Denied access clears the whole parent expense workspace and retains the opaque original.

An absent original remains retained. Explicit Review the original record again opens the normal reviewed workflow with the original identity supplied only to the matching saved bill/payable. Other supplier posting forms stay disabled. The user must re-enter/review private details and confirm; the request reuses the original operation/recovery/posting identity. A late original commitment remains subject to the unchanged server idempotency and evidence rules. Conflicting root lookup is retained and blocked; no uncertain financial history is silently retired or deleted.

Mounted explicit retries continue using their existing in-memory input. Definitive refused write results keep the existing refresh/review behavior and remove only the exact original reference after verification. An operation conflict retains the original and directs an explicit lookup; it does not release a possibly already-used identity or enable a fresh posting. Storage failures block another posting. No browser-storage value authorizes a request.
